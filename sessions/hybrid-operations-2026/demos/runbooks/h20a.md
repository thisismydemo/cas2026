# H20A — Inspect a Defender for Cloud finding for an Arc-enabled server

Slide 33 · Rehearsal target: 3 minutes

What this demo shows and why: Defender for Cloud only shows findings for a server when its Defender for Servers plan is on and the Defender for Endpoint sensor runs on that server. We follow that chain on one Arc-enabled AWS server: check the coverage, open one real finding about what is weak (a security recommendation), and turn it into an action with an owner and a way to prove it was fixed. A finding nobody owns is just a red badge.

## Before delivery

- Names used in this runbook: the target is iic-cas26-prd-api-01, one of the sample application's Linux EC2 servers, Arc-enabled through the connector (Ec2ArcResourceId); AWS_<AccountId> is the connector-created resource group.
- To reproduce: Defender for Servers enabled on the subscription, an Arc-enabled server with the Defender for Endpoint sensor, Security Reader (or higher) in Defender for Cloud, and Azure CLI with the resource-graph extension.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: Defender for Servers Plan 2 is enabled on the workload, management and security subscriptions. Confirm coverage for the AWS and on-premises Arc machines before either session; Arc registration by itself is not Defender coverage.
- Presenter lab: preselect one current Linux security-baseline recommendation on the target machine (each IIC Linux machine carries about 40 hardening findings). Never introduce a vulnerability into the shared environment to create one.
- Presenter lab: record the finding's resource ID, assessment time, evidence, remediation owner, change window and how the fix will be verified. Keep unrelated security findings off the projected screen.

## 1. Pick the exact server

Mode: read-only

Load context and show the selected EC2 Arc machine. Then open Microsoft Defender for Cloud > Inventory in the portal and filter to the AWS_<AccountId> resource group and this machine's name.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
az resource show --ids $Demo.Ec2ArcResourceId --query '{id:id,name:name,tags:tags}' -o json
```

**Expected evidence:** The machine's ID, name and tags in the terminal, and the same machine in Defender for Cloud's inventory; similarly named resources are excluded.

**If this fails:** If the machine is missing from the inventory, check the portal's directory and subscription filter. A similarly named machine elsewhere is not a substitute: show the rehearsal capture.

**Speaker explanation:** Say: the same AWS server we have been following. First make sure the portal and the terminal look at the same machine.

**Attendee takeaway:** Start a security investigation by pinning down the exact resource ID.

## 2. Check the chain: plan and sensor

Mode: portal

In Defender for Cloud > Environment settings, open the subscription and show Defender for Servers is On (Plan 2). Then, on the machine's page in Inventory, show that the Defender for Endpoint sensor (the MDE.Linux extension) is installed and healthy, and read when the machine was last assessed. Not every plan uses the Log Analytics workspace; say which component supplies this evidence.

**Expected evidence:** Defender for Servers Plan 2 On for the subscription; the machine shows the Defender for Endpoint sensor installed and a recent assessment time. A missing sensor or a stale assessment is visible, not hidden.

**If this fails:** If coverage shows a gap, name it as a configuration finding: without the plan and the sensor there are no vulnerability findings or security alerts from this path. Never enable a billable plan on stage to fill the page.

**Speaker explanation:** Say: this is the chain from the last slide. You turn on the Defender for Servers plan; the plan puts the Defender for Endpoint sensor on the server; what the sensor finds comes back here. No plan, no sensor, no findings.

**Attendee takeaway:** Check plan and sensor coverage before trusting an empty findings list.

## 3. Open one finding: what is weak

Mode: portal

From the machine, open Recommendations and choose the preselected Linux security-baseline recommendation. Read the affected resource, severity, status, the last assessment time and which setting is wrong. Follow attack-path context only if the page actually shows it.

**Expected evidence:** One recommendation tied to this exact machine, with severity, status Unhealthy, an assessment time and the failing configuration: an attributable target and evidence, not merely a severity badge.

**If this fails:** If the chosen recommendation no longer applies, show that as a legitimate change. Do not substitute an unrelated finding or imply unavailable attack-path features are enabled.

**Speaker explanation:** Say: this is posture, what is weak. A security alert would be protection, what is under attack. They are different results and they go to different people.

**Attendee takeaway:** Recommendations say what is weak; security alerts say what is under attack. Know which one you are looking at.

## 4. Decide who fixes it

Mode: portal

Open the recommendation's remediation steps. Say who owns the fix, what access they need, when it can be done, what it could affect and how you will check it worked. Show the owner in the team's existing workflow (for example the recommendation's owner assignment or a ticket) rather than inventing one on stage.

**Expected evidence:** A named owner (person or team), a change window and a verification step for this one finding; a resource Owner tag alone does not prove anyone accepted the work.

**If this fails:** If a patch/reboot would disrupt the shared service, explain the planned action rather than performing it. The demo goal is evidence-to-decision, not an improvised production change.

**Speaker explanation:** Say: the chain ends with an owner. A finding with no owner does not get fixed, and an Owner tag on the resource is not the same as someone accepting the work.

**Attendee takeaway:** Every finding needs an owner, a window and a way to verify the fix.

## 5. Check how fresh the status is

Mode: read-only

Run the Resource Graph query. It lists every Defender assessment for this machine with its status, severity, when it was first evaluated and when its status last changed. If a fix was applied during preparation, show the before and after with their times; otherwise name the planned change and its window.

```powershell
$q = "securityresources | where type == 'microsoft.security/assessments' | where tostring(properties.resourceDetails.Id) =~ '$($Demo.Ec2ArcResourceId)' | project Recommendation=tostring(properties.displayName), Status=tostring(properties.status.code), Severity=tostring(properties.metadata.severity), FirstEvaluated=todatetime(properties.status.firstEvaluationDate), StatusChanged=todatetime(properties.status.statusChangeDate) | order by Status asc, Severity asc"
az graph query --subscriptions $Demo.SubscriptionId -q $q --first 100 -o table
```

**Expected evidence:** A table of this machine's assessments with Healthy or Unhealthy status and their dates; the chosen finding is present with its status-change date. Assessment refresh delay is acknowledged.

**If this fails:** A successful patch command is not automatically a refreshed Defender assessment. Do not mark the finding resolved based solely on command completion.

**Speaker explanation:** Say: a status is only as good as its timestamp. A fix is proven when a fresh assessment says Healthy, not when the patch command finishes.

**Attendee takeaway:** A finding is fixed when a fresh assessment says so, not when the change command completes.

## 6. Debrief and hand over to Sentinel

Mode: portal

Summarize: coverage checked, one finding on the exact server, an owner, and fresh evidence to prove the fix. Recall who is allowed to act from the RBAC demo. Transition: Defender for Cloud shows what is weak or under attack on each resource; Microsoft Sentinel brings security data from servers and cloud services into one workspace and turns it into incidents.

**Expected evidence:** The audience can tell a Defender recommendation from a security alert and from a Sentinel incident.

**If this fails:** Nothing to run here. If an earlier step fell back to a capture, name what it would have shown before moving on.

**Speaker explanation:** Say: one finding, deep enough to act on; we are not touring every Defender page. Transition: Microsoft Sentinel, where security data from many sources becomes one investigation.

**Attendee takeaway:** Security findings become useful when target, freshness, owner and verification are clear. Service coverage and data integrations determine what evidence is available.

## Reset and verification

Read-only by default. Preserve real security records and audit history. Do not dismiss findings, weaken controls or reboot shared workloads as a reset.

## If the live demo fails

If Defender for Cloud is slow to load, show the rehearsal capture of the finding with its resource ID, assessment time and owner, and name the step you would have run. Never invent a finding to fill an empty screen.

## Timing and handoff

Assessments refresh on the service's schedule. Read the assessment time rather than waiting for a refresh, and never promise immediate clearance after a change.
