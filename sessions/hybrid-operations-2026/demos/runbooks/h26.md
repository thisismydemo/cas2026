# H26 — Manage the already-onboarded EKS cluster with Flux

Slide 49 · Rehearsal target: 3.5 minutes

What this demo shows and why: with GitOps, Git holds the desired state of a Kubernetes cluster, Flux (running in the cluster) keeps the cluster matching it, and Azure shows whether it matches. We do this on the AWS EKS cluster that the connector onboarded to Arc earlier: point Flux at a reviewed folder in Git and prove that the small ConfigMap it declares really appears in the cluster. AWS still owns the EKS cluster itself; Arc and Flux govern what runs on it.

- To reproduce: an Arc-enabled Kubernetes cluster with the microsoft.flux extension, a Git repository containing the kustomization folder from this repository, kubectl with a context for the cluster, and Azure CLI with the connectedk8s and k8s-configuration extensions.

Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: verify the EKS account, region and ARN, the matching Arc connectedClusters ID (eks-iic-cas26-use2-01, Connected), the Kubernetes context, the Arc agents, the Flux extension and repository access. Never reconnect an existing Arc cluster.
- Presenter lab: reserve Flux configuration cas26-demo and namespace cas26-demo exclusively for this exercise; neither may contain unrelated objects. Review the repository/branch and exact commit before live creation. The manifests include a Namespace plus a ConfigMap, requiring cluster scope.
- Presenter lab: preinstall and verify the shared microsoft.flux extension and required CLI extensions. Configure private repository authentication separately without showing credentials. Do not put tokens into demo.local.json or command history.
- Presenter lab: use a dedicated reviewed branch that will not change unexpectedly during the session. Review and record its current commit; prune=true can delete owned objects, including the namespace in this repository.

## 1. The same EKS cluster, now as an Arc resource

Mode: read-only

Load context, split the Arc cluster ID into its resource group and name, and run the two commands: the Arc cluster's connection state, then the local kubectl context. Compare the EKS ARN noted in the connector demo with the prepared mapping and the kubectl context before running any cluster command.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
$clusterParts = $Demo.EksArcResourceId.Split('/')
$ClusterRg = $clusterParts[4]
$ClusterName = $clusterParts[8]
az connectedk8s show --resource-group $ClusterRg --name $ClusterName --query '{id:id,connectivity:connectivityStatus,provisioning:provisioningState}' -o json
kubectl config get-contexts $Demo.KubernetesContext
```

**Expected evidence:** A Microsoft.Kubernetes/connectedClusters resource with connectivity Connected for the intended EKS cluster (not AKS, not a server), and the configured kubectl context listed.

**If this fails:** If the cluster shows Offline or the context is missing, stop: check KubernetesContext and EksArcResourceId in demo.local.json and show the rehearsal capture. Never substitute another cluster.

**Speaker explanation:** Say: remember the EKS cluster from the connector demo; this is how you govern it. AWS still owns the EKS cluster itself; Arc and Flux govern what runs on it.

**Attendee takeaway:** Confirm the exact Arc-enabled Kubernetes cluster and kubectl context before any cluster command; the EKS cluster appears in Azure as a connected cluster, not as AKS or a server.

## 2. Check what is already there

Mode: read-only

Run the four commands: installed cluster extensions, existing Flux configurations, then the cas26-demo namespace and ConfigMap (every kubectl command names the context explicitly). If cas26-demo already exists, it must be proven to belong to this exercise; a matching name alone is not enough.

```powershell
az k8s-extension list --cluster-name $ClusterName --resource-group $ClusterRg --cluster-type connectedClusters -o table
az k8s-configuration flux list --cluster-name $ClusterName --resource-group $ClusterRg --cluster-type connectedClusters -o table
kubectl --context $Demo.KubernetesContext get namespace cas26-demo --ignore-not-found
kubectl --context $Demo.KubernetesContext get configmap cas26-operating-contract --namespace cas26-demo --ignore-not-found -o yaml
```

**Expected evidence:** The microsoft.flux extension installed; either no cas26-demo configuration yet or one that points at the reviewed repository; the namespace and ConfigMap absent or clearly owned by this exercise.

**If this fails:** If namespace ownership is uncertain or Flux config points elsewhere, stop. Do not adopt/delete an existing resource or extension to force the exercise.

**Speaker explanation:** Say: before changing a cluster, look at what is already there: the Flux extension, any existing configuration, and the namespace we will use.

**Attendee takeaway:** Know what a cluster already runs (extensions, Flux configurations, namespaces) before you add desired state to it.

**Attendee takeaway:** Review the exact commit Flux will apply; the remote branch, not your local copy, is the source of truth.

## 4. Point Flux at the reviewed folder

Mode: change

If cas26-demo already exists from rehearsal and matches the reviewed source, skip this command and inspect it in step 5. Otherwise run it: it creates a Flux configuration on the Arc cluster that watches the branch and applies the kustomization folder. Cluster scope is needed because the manifest contains a Namespace; it does not authorize any other repository.

```powershell
az k8s-configuration flux create --cluster-name $ClusterName --resource-group $ClusterRg --cluster-type connectedClusters --name cas26-demo --namespace flux-system --scope cluster --url $Demo.FluxRepositoryUrl --branch $Demo.FluxBranch --kustomization name=cas26 path=./sessions/hybrid-operations-2026/demos/src/sample-service/kubernetes prune=true
if ($LASTEXITCODE -ne 0) { throw 'The operation failed. Stop and follow the recovery instructions.' }
```

**Expected evidence:** The CAS26 Flux configuration references only the approved source/path. Configuration creation is not yet proof that objects were applied.

**If this fails:** If the create fails, read the error: repository authentication, Flux extension provisioning or a name clash with an existing configuration. Show the rehearsal capture; never swap in an unreviewed repository or install broader cluster components on stage.

**Speaker explanation:** Say: we tell Azure, and Azure tells Flux in the cluster: watch this folder on this branch and keep the cluster matching it.

**Attendee takeaway:** A Flux configuration tells the cluster which repository, branch and folder to follow; creating it is not yet proof that anything was applied.

## 5. Is the cluster matching Git?

Mode: read-only

Run the commands: the Flux configuration as Azure sees it (compliance state, source revision, kustomization status), then the GitRepository and Kustomization objects inside the cluster. Compare the revision with the commit recorded in step 3; a branch name alone does not prove matching content.

```powershell
az k8s-configuration flux show --cluster-name $ClusterName --resource-group $ClusterRg --cluster-type connectedClusters --name cas26-demo -o json
kubectl --context $Demo.KubernetesContext get gitrepositories,kustomizations --namespace flux-system -o wide
```

**Expected evidence:** complianceState Compliant with the source revision equal to the recorded commit, and Ready True for the GitRepository and Kustomization in flux-system; or an explicit pending or error state that is read aloud.

**If this fails:** Azure status can lag in-cluster reconciliation. Inspect controller conditions/events through the scoped configuration rather than declaring success from Succeeded provisioning alone.

**Speaker explanation:** Say: this is Azure showing whether the cluster matches what Git says, at which commit.

**Attendee takeaway:** Azure reports whether the cluster matches Git and at which commit; check the revision, not just a green status.

## 6. See the object in the real cluster

Mode: read-only

Read the ConfigMap from the explicit context and namespace. Compare its data with the file reviewed in step 3. Never kubectl apply the object by hand and then claim Flux reconciled it.

```powershell
kubectl --context $Demo.KubernetesContext get configmap cas26-operating-contract --namespace cas26-demo -o yaml
```

**Expected evidence:** owner=hybrid-operations, change-boundary=dedicated-demo-namespace and expected-state=reconciled-by-azure-arc-flux match the source, together with successful reconciliation evidence.

**If this fails:** Object presence without revision/controller evidence could be a previous/manual object. Preserve the distinction.

**Speaker explanation:** Say: and here it is in the cluster itself: the ConfigMap Git declared, applied by Flux, not by me.

**Attendee takeaway:** Check the object in the cluster itself and compare it with Git; its presence alone could be a leftover or a manual change.

## 7. Before any cleanup: check what would be deleted

Mode: read-only

Normally leave the configuration in place for the other session. If you are resetting between rehearsals, run the block: it lists every namespaced resource in cas26-demo, of every kind. Because the Git folder includes the Namespace and prune=true is set, deleting the configuration can remove that namespace and everything in it. Stop if anything there is not owned by this exercise.

```powershell
$kinds = kubectl --context $Demo.KubernetesContext api-resources --namespaced=true --verbs=list -o name
foreach ($kind in $kinds) { kubectl --context $Demo.KubernetesContext get $kind --namespace cas26-demo --ignore-not-found -o name }
# Review all results and ownership before considering configuration deletion.
```

**Expected evidence:** The reset impact is understood. Shared extension, Arc agents, connector and EKS cluster are never reset by this exercise.

**If this fails:** An enumeration error is an incomplete ownership check, not permission to delete. Do not rely on kubectl get all; it omits resource kinds.

**Speaker explanation:** Say: pruning is powerful: remove it from Git and Flux removes it from the cluster. So before any cleanup, look at everything the namespace holds.

**Attendee takeaway:** With prune enabled, removing something from Git removes it from the cluster; check everything a namespace holds before any cleanup.
