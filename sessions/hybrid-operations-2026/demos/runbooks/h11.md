# H11 — Add AWS resources through the Arc multicloud connector

Slide 15 · Rehearsal target: 2 minutes

What this demo shows and why: the Arc multicloud connector is one Azure resource that is given access to an AWS account, brings its resources into Azure and can onboard its EC2 servers and EKS clusters to Arc. We walk the four steps from the previous slides on a real connector: give Azure access, the connector, it brings things in, you manage them. The point is to tell three results apart: an AWS resource Azure only lists (inventory), an EC2 server that became an Arc-enabled server, and an EKS cluster that became an Arc-enabled Kubernetes cluster.

## Before delivery

- Names used in this runbook: pcc-tplabs-cas26-aws-eus-01 is the presenter's existing multicloud connector; AWS_<AccountId> is the resource group the connector creates for AWS resources (the portal may show it in lower case, aws_<accountId>); eks-iic-cas26-use2-01 is the EKS cluster; the eight EC2 machines are the six application servers of IIC Hybrid Orders (the sample application used throughout the session) plus two SQL Server machines; Event:cas26 is the AWS tag the connector filters on.
- To reproduce: an AWS account where you can deploy the connector's CloudFormation template, an Azure subscription with the Microsoft.HybridConnectivity and Microsoft.HybridCompute resource providers registered, Contributor on the target resource group, and Azure CLI with the resource-graph, connectedmachine and connectedk8s extensions.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: the connector already exists; this demo inspects it and never creates one. Before delivery, review the AWS CloudFormation stack, account, regions, tag filters, connector identity and the enabled solutions.
- Presenter lab: the landing-zone baseline (access, Defender, Sentinel, Policy) must cover the connector-created AWS_<AccountId> resource group; an operations-resource-group policy does not reach it. Check its effective baseline before allowing onboarding.
- Presenter lab: discovery and onboarding run on the connector's own schedule. Do not create a duplicate Arc connection; the demo shows the configured solutions, the last sync time and the verified results.

## 1. Find the connector and the AWS account behind it

Mode: read-only

Load context (first line), then list the multicloud connectors in the subscription. In a browser tab next to the terminal, show the AWS console for the same account and region (no credentials on screen) and point at one EC2 instance ID and the EKS cluster ARN; step 5 follows those two into Azure.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
az resource list --resource-type Microsoft.HybridConnectivity/publicCloudConnectors --query '[].{name:name,id:id,resourceGroup:resourceGroup}' -o table
```

**Expected evidence:** One connector, pcc-tplabs-cas26-aws-eus-01, with its resource group. The AWS tab shows the same account; the workloads stay in AWS.

**If this fails:** If no connector is listed, check the signed-in subscription (az account show) first; the connector lives in the workload subscription. If several are listed, use the one above and say the others are out of scope.

**Speaker explanation:** Say: the first step on the slide was give Azure access; the second is the connector itself. This is it: one Azure resource pointing at one AWS account. Nothing moved out of AWS.

**Attendee takeaway:** The connector is an Azure resource tied to one AWS account; the AWS workloads do not move.

## 2. See which solutions the connector offers

Mode: read-only

Run the lab helper below. It lists the solution types the connector service currently publishes for this subscription (inventory, Arc server onboarding, EKS onboarding and others) and the settings each accepts. We only read the list; nothing is changed.

```powershell
pwsh ./shared/foundation/scripts/Get-Cas26ConnectorSolutionTypes.ps1
```

**Expected evidence:** A list of the available solution types and their settings, including inventory and the Arc onboarding solutions.

**If this fails:** If it fails with a provider-registration or permission error, say so and show the rehearsal capture of the list. Do not register providers or change settings on stage.

**Speaker explanation:** Say: the connector does nothing on its own; you choose solutions. Inventory only lists what exists. The onboarding solutions put the Arc agent on a server, or the Arc agents on a cluster.

**Attendee takeaway:** A connector's solutions are separate choices: inventory lists resources; onboarding solutions make them Arc-enabled.

## 3. Walk the access grant and the chosen solutions

Mode: portal

In the Azure portal, open Azure Arc > Multicloud connectors > pcc-tplabs-cas26-aws-eus-01. Show the AWS account and regions, the Event:cas26 tag filter, and each solution (Inventory, Arc server onboarding, EKS onboarding, monitoring) with its last sync time. Then, in the AWS console, open the CloudFormation stack the connector asked us to deploy and show the IAM role it created: that role is how Azure was given access. Do not add or change anything.

**Expected evidence:** The access grant (CloudFormation stack and its role), the tag filter and each solution's state and last sync time are visible; no new permission is granted.

**If this fails:** If the stack shows an error or a solution is unhealthy, name it as a setup problem and show the rehearsal capture. Never widen the AWS role or remove the tag filter to make more resources appear.

**Speaker explanation:** Say: this is 'give Azure access': a CloudFormation stack in AWS creates a role Azure may use, and nothing broader. The tag filter means only resources tagged Event:cas26 come in.

**Attendee takeaway:** Access is granted on the AWS side by a CloudFormation-created role; tag filters limit what the connector brings in.

## 4. Where the AWS resources land in Azure

Mode: read-only

Run the command to show the connector-created resource group and its tags. In the portal, open that resource group's Access control (IAM) and Policies pages and show that the same landing-zone rules apply here as to the on-premises machines.

```powershell
az group show --name $Demo.AwsResourceGroup --query '{id:id,name:name,tags:tags}' -o json
```

**Expected evidence:** The AWS_<AccountId> resource group with its tags; its role assignments and policy assignments are visible in the portal.

**If this fails:** A name that differs only in case (aws_<accountId>) is the same group. If the group is not found, compare AwsResourceGroup in demo.local.json with the portal.

**Speaker explanation:** Say: 'it brings things in', and they land in their own resource group. That group needs the same access, security and Policy rules as everything else, or the AWS servers become the unmanaged corner of the estate.

**Attendee takeaway:** The connector creates its own resource group; make sure your landing-zone access and policy rules cover it.

## 5. Tell the three results apart

Mode: read-only

Run the four commands. The first uses Azure Resource Graph, because inventory records (the awsresources table) are not returned by an ordinary resource list. Then map each result: awsresources = Azure knows the AWS resource exists; Microsoft.HybridCompute/machines = an EC2 server that is now an Arc-enabled server; Microsoft.Kubernetes/connectedClusters = the EKS cluster, now an Arc-enabled Kubernetes cluster. Match the EC2 instance ID and EKS ARN from step 1 to these resources.

```powershell
az graph query --subscriptions $Demo.SubscriptionId -q "awsresources | where resourceGroup =~ '$($Demo.AwsResourceGroup)' | summarize count() by type" -o table
az resource list --resource-group $Demo.AwsResourceGroup --resource-type Microsoft.HybridCompute/machines --query '[].{name:name,status:properties.status,id:id}' -o table
az resource show --ids $Demo.Ec2ArcResourceId --query '{id:id,status:properties.status,agentVersion:properties.agentVersion,tags:tags}' -o json
az connectedk8s show --ids $Demo.EksArcResourceId --query '{id:id,connectivity:connectivityStatus,provisioning:provisioningState}' -o json
```

**Expected evidence:** A count of AWS inventory by type; the eight EC2 Arc machines with status Connected; one EC2 Arc machine in detail (status Connected, agent version, tags); and the EKS cluster with connectivity Connected. Inventory presence alone does not prove an agent or cluster connection.

**If this fails:** If a resource sits in an alternative resource group configured in demo.local.json, use that exact ID and say why. Never pair resources by display name alone. If Resource Graph is slow, show the rehearsal capture.

**Speaker explanation:** Say: three results, three different things. Inventory is only a list. An Arc-enabled server has the agent. An Arc-enabled Kubernetes cluster has the Arc agents inside the cluster. EKS is still EKS; it has not become AKS.

**Attendee takeaway:** Inventory, an Arc-enabled server and an Arc-enabled Kubernetes cluster are different states; inventory alone does not mean an agent is connected.

## 6. Hand these resources to the rest of the session

Mode: portal

Read the result aloud: all eight CAS26 EC2 machines (six IIC application servers plus two SQL Server machines) are Arc Connected, and the EKS cluster eks-iic-cas26-use2-01 is Connected as an Arc-enabled Kubernetes cluster. Say which ones come back: EC2 machines in the Observe, Secure and Policy demos, and the EKS cluster in the Flux demo. Transition: edge sites and legacy servers, where Arc still needs an outbound connection to Azure.

**Expected evidence:** The audience knows which AWS resources the later demos use; no management result is claimed yet.

**If this fails:** If a machine or the cluster shows Disconnected, say so and name the later demo it affects; never claim Connected from an inventory entry.

**Speaker explanation:** Say: 'you manage them' is the rest of the session. A resource list is not management: later we change a Policy-managed tag on one of these EC2 servers and reconcile Kubernetes objects on this EKS cluster. Transition: edge sites and legacy servers.

**Attendee takeaway:** The connector gets AWS resources into Azure; monitoring, security, Policy and GitOps are the separate management steps that follow.

## Reset and verification

Leave connector, source authorization and Arc resources intact for both sessions. No live reset; repeated onboarding is not the reset mechanism.
