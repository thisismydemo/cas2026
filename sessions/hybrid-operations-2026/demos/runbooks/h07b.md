# H07B — Connect the on-premises/edge machines to Azure Arc

Slide 8 · Rehearsal target: 2.5 minutes

What this demo shows and why: a Windows server in our own datacenter gets the Azure Connected Machine agent and becomes a resource in Azure, with one outbound connection and no inbound ports or VPN. We prove it worked from both sides, on the machine and in Azure, because an installer that exits cleanly is not proof. Connecting only makes the server manageable; monitoring, security and Policy are separate steps shown later in the session.

## Before delivery

- Names used in this runbook: cas26-arcwin01 is the presenter's on-premises Windows Server virtual machine (the demo target); MGMT-RAL-HV-01 is the standalone Hyper-V host it runs on; rg-tplabs-cas26-ops-eus-01 is the Azure resource group it lands in (the 'operations resource group'); Event=cas26 is the tag the lab puts on its own machines. To reproduce, substitute your own server, subscription and resource group.
- To reproduce: a supported Windows Server with outbound HTTPS (443) to the Azure Arc endpoints, local administrator rights on it, an Azure identity allowed to onboard servers into <your-resource-group> (for example the Azure Connected Machine Onboarding role), and Azure CLI plus PowerShell 7 on your workstation.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: shared/foundation/config/variables.yml drives Connect-Cas26Arc.ps1, independently of demo.local.json. Confirm on_prem.windows_guest.name=cas26-arcwin01, cluster_node=MGMT-RAL-HV-01 (by exact IP, with its local credential), cluster_role=false, and the tenant, subscription and operations resource group, before any installation.
- Presenter lab: cas26-arcwin01 is booted, network-attached and reachable from the presenter jump; its local administrator credential is in the CAS26 Key Vault; the Arc endpoints resolve and are reachable outbound; the agent package is pre-staged. Edge means connected edge: no disconnected-management promise.
- Presenter lab: the guest lands in rg-tplabs-cas26-ops-eus-01 with Event=cas26 and no Owner tag; the Policy demo (slide 42) depends on that missing tag. If it is still connected from rehearsal, the helper reports the existing resource and the demo inspects it; never disconnect a working shared machine to restage. The Linux guest cas26-lnx01 runs on the SCVMM cluster and was brought into Arc through SCVMM (slides 9-11), not by this demo.

## 1. Show which Azure account and which machine we are using

Mode: read-only

In the presenter terminal (PowerShell 7, repository root), run the two lines below. The first loads the demo identifiers into $Demo and refuses to continue if the signed-in tenant or subscription differs from the configuration; the second prints the signed-in account. Then say which machine we connect (cas26-arcwin01) and where it runs (Hyper-V host MGMT-RAL-HV-01 in our datacenter).

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
az account show --query '{tenant:tenantId,subscription:id,name:name,user:user.name}' -o json
```

**Expected evidence:** 'Demo configuration validated (current Azure context)', then a JSON block whose tenant and subscription match demo.local.json and whose user is the presenter's onboarding identity.

**If this fails:** A tenant/subscription mismatch is a stop: run az account set --subscription <workload subscription> (the jump defaults to the management subscription) and rerun. If it asks you to populate a field, fix demo.local.json. Never carry on under a different account.

**Speaker explanation:** Say: before we touch anything, this is the Azure account we are using and this is the one server we are connecting, a Windows VM on a Hyper-V host in our own datacenter.

**Attendee takeaway:** Confirm the tenant, subscription and target machine before onboarding; the common mistake is the right machine landing in the wrong place.

## 2. Preview what the onboarding script will do

Mode: read-only

Run the preview. Connect-Cas26Arc.ps1 is the lab's wrapper around standard Arc onboarding: it opens a session on the guest, installs the Azure Connected Machine agent and runs azcmagent connect. -DryRun prints the target and settings without changing anything. Point at three things in the output: the guest name, the resource group and the Event=cas26 tag.

```powershell
pwsh ./shared/foundation/scripts/Connect-Cas26Arc.ps1 -Target Windows -DryRun
if ($LASTEXITCODE -ne 0) { throw 'The operation failed. Stop and follow the recovery instructions.' }
```

**Expected evidence:** The preview names only cas26-arcwin01, the operations resource group and the Event=cas26 tag; it asks for no cluster node or Linux address. Nothing is installed.

**If this fails:** If the preview names another guest, resource group or subscription, stop: fix shared/foundation/config/variables.yml and rerun the preview. If it throws, read the error aloud and switch to the rehearsal capture; do not run step 3 against an unverified target.

**Speaker explanation:** Say: this does what the portal's 'Add a server' script does: install one agent, make one outbound connection. The preview shows where it will land, and that resource group decides which access and Policy rules it inherits.

**Attendee takeaway:** Where a server lands (subscription and resource group) decides which rules it inherits, so check it before connecting.

## 3. Connect the server

Mode: change

Run the same command without -DryRun. It installs the agent if needed and connects the guest. If the guest is still connected from rehearsal, the script reports the existing resource instead of reconnecting; that is fine, carry on. Never show access tokens, credentials or temporary token files on screen.

```powershell
pwsh ./shared/foundation/scripts/Connect-Cas26Arc.ps1 -Target Windows
if ($LASTEXITCODE -ne 0) { throw 'The operation failed. Stop and follow the recovery instructions.' }
```

**Expected evidence:** The script finishes without an error and reports the Arc resource for cas26-arcwin01, newly connected or already connected.

**If this fails:** If sign-in, outbound access to the Arc endpoints or the package install fails, keep the error on screen, say which one failed and show the rehearsal capture. Do not rerun against another target and never disconnect another Arc machine to retry.

**Speaker explanation:** Say: one outbound connection on port 443, no inbound ports, no VPN. The application on this server never uses this connection.

**Attendee takeaway:** Arc onboarding is one agent and one outbound HTTPS connection; the workload itself is untouched.

## 4. Check the agent on the server itself

Mode: read-only

Switch to the administrative PowerShell session on cas26-arcwin01 (RDP or a remote session from the jump) and run azcmagent show. Read out the resource name, resource group, subscription, tenant and Agent Status.

```powershell
azcmagent show
```

**Expected evidence:** Agent Status: Connected, with resource name cas26-arcwin01, the operations resource group and the same tenant and subscription as step 1. A successful installer exit alone is not enough.

**If this fails:** If azcmagent is not recognised, run it by full path: & 'C:\Program Files\AzureConnectedMachineAgent\azcmagent.exe' show. If the status is Disconnected, run azcmagent check on the guest to test the endpoints, then show the rehearsal capture. The portal alone cannot prove which machine's agent is connected.

**Speaker explanation:** Say: proof has two sides. This is the machine's side: the agent says it is connected, and to which Azure resource.

**Attendee takeaway:** Check the agent on the machine (azcmagent show) as well as the portal; an installer that exits cleanly is not proof.

## 5. Check the same machine in Azure

Mode: read-only

Back in the presenter terminal, run the command. Compare the resource ID with what azcmagent show printed, then point at the system-assigned managed identity (the machine's own identity in Microsoft Entra ID, used later by extensions) and the tags.

```powershell
az resource show --ids $Demo.OnPremArcResourceId --query '{id:id,type:type,location:location,identity:identity,tags:tags,properties:properties}' -o json
```

**Expected evidence:** One Microsoft.HybridCompute/machines resource named cas26-arcwin01 in the operations resource group, identity type SystemAssigned, status Connected, and tags that include Event=cas26 but no Owner tag.

**If this fails:** The Azure view can lag the agent by a minute; rerun once. A machine with a similar name in another resource group is not a match: show the rehearsal capture instead.

**Speaker explanation:** Say: and this is Azure's side: the same machine, now an Azure resource with its own identity and tags. Notice it has no Owner tag; we come back to that in the Policy demo.

**Attendee takeaway:** The Arc resource and the agent must agree on the same resource ID; that is what 'connected' means.

## 6. What connecting did, and did not, do

Mode: read-only

In the portal open Azure Arc > Machines > cas26-arcwin01 and show the Extensions page. Run the command to list the Arc machines in the operations resource group. Name what later demos add to this same resource: the Azure Monitor agent with its data collection rule (DCR) association, Defender for Cloud coverage, the Owner-tag policy and the Sentinel training event. Transition: the software that already runs these VMs, SCVMM and vCenter.

```powershell
az resource list --resource-group $Demo.OperationsResourceGroup --resource-type Microsoft.HybridCompute/machines --query '[].{name:name,id:id}' -o table
```

**Expected evidence:** cas26-arcwin01 is in the list with the other on-premises Arc machines; the audience can see that Connected means manageable, not yet monitored, secured or proven to work.

**If this fails:** If the list is slow or empty, stay on the portal page from step 5 and make the same point; nothing later depends on this command.

**Speaker explanation:** Ask: which resource can we now govern? Then debrief: connecting creates the Azure representation; it does not turn on monitoring, Defender or Policy, and it says nothing yet about whether the application works. Transition: we connected these machines from the inside; next, the software that already runs these VMs, SCVMM and vCenter.

**Attendee takeaway:** Connecting makes a server manageable through Azure. Monitoring, security coverage, compliance and application health each need their own setup and their own evidence.

## Reset and verification

Keep the Arc connection: the Sentinel, Policy and Update Manager demos use this machine. Never disconnect and reconnect a shared machine between sessions; tearing down the lab after the event is a separate reviewed procedure.

## If the live demo fails

If installation or the portal is slow, show the rehearsal capture that pairs azcmagent show output with the matching Azure resource ID, and say which step you would have run.

## Timing and handoff

Agent installation and connection run asynchronously, and the Azure view can lag the agent by a minute. Pre-stage the agent package and keep the rehearsal capture ready instead of polling on stage.
