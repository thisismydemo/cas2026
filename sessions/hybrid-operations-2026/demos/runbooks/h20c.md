# H20C — Investigate a Microsoft Sentinel incident

Slide 35 · Rehearsal target: 2 minutes

What this demo shows and why: Microsoft Sentinel collects security data into a Log Analytics workspace, runs detection rules over it and raises incidents for an analyst to own. We follow one harmless, clearly labelled training event from a Windows server (collected by the Azure Monitor agent under a data collection rule) through a detection rule into an incident, then record an owner and a decision. Nothing here is a real attack.

## Before delivery

- Names used in this runbook: cas26-arcwin01 is the on-premises Windows server connected in the first demo; law-tplabs-cas26-security-eus-01 is the Log Analytics workspace with Sentinel enabled; CAS26Demo is the event source and 2601 the event ID of the training event; incidents from the training rule are titled CAS26 TRAINING.
- To reproduce: a Sentinel-enabled workspace; a Windows Arc-enabled server with the Azure Monitor agent and a data collection rule (DCR) that sends Application-log events to that workspace; a scheduled analytics rule on the training marker (src/queries/sentinel-training-event.kql); and Microsoft Sentinel Responder to assign and close incidents.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: Sentinel is onboarded on law-tplabs-cas26-security-eus-01 with the CAS26 training analytics rule. cas26-arcwin01 has AMA and a DCR association that routes Application-log events into that workspace. Confirm the rule and its incident settings; both sessions use the same shared baseline.
- Presenter lab: run the training event before the live slot and confirm that the event and the incident actually exist. Read scripts/Write-Cas26Event.ps1 before choosing where to run it (it needs Windows).
- Limit the view to CAS26 TRAINING incidents. Do not simulate malicious behavior, change production detection rules or close unrelated incidents.

## 1. Confirm the Sentinel workspace

Mode: read-only

Load context and show the Sentinel workspace resource. In the Defender portal (or Microsoft Sentinel in the Azure portal), open the same workspace and set the time range to the last 24 hours. The full resource ID proves which workspace; its GUID (customer ID) is what the query commands in steps 3 and 4 use.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
az resource show --ids $Demo.SentinelWorkspaceResourceId --query '{id:id,name:name,location:location}' -o json
```

**Expected evidence:** The workspace name law-tplabs-cas26-security-eus-01 and its location, and the portal on the same workspace; not a similarly named one.

**If this fails:** If the read fails, check SentinelWorkspaceResourceId in demo.local.json; the workspace sits in the security subscription, so the signed-in account needs read access there too.

**Speaker explanation:** Say: the Sentinel slide said everything lands in one workspace. This is that workspace.

**Attendee takeaway:** Confirm the workspace before reading incidents; a similarly named workspace can hold different data.

## 2. The harmless training event and the rule

Mode: preparation

Before the session, on cas26-arcwin01, in PowerShell 7 at the repository root, run the command below. It writes one Information event (source CAS26Demo, ID 2601) to the Windows Application log. If CAS26Demo is not registered yet, run the script once with -RegisterSource in an elevated session first. Never run it on the presenter laptop. On stage, open Sentinel > Analytics and show the training rule: its query, schedule and incident settings.

```powershell
# On the selected Windows guest, from its repository root:
pwsh ./sessions/hybrid-operations-2026/demos/scripts/Write-Cas26Event.ps1 -Message 'CAS26 Sentinel training'
if ($LASTEXITCODE -ne 0) { throw 'Training event creation failed.' }
# The source must already have been registered during preparation.
```

**Expected evidence:** Before the session: the script exits cleanly on the guest. On stage: the rule's query matches the CAS26Demo marker, with its frequency and incident creation turned on. It matches a known synthetic marker; it does not claim to detect a real attack.

**If this fails:** If the script says the source is not registered, run it once with -RegisterSource in an elevated session on the guest and rerun. If the rule is disabled or missing, show the rehearsal capture; never edit a shared rule on stage.

**Speaker explanation:** Say: this event is a harmless marker we wrote on purpose so the rule has something to find. It is not an attack, and the rule does not claim to detect one.

**Attendee takeaway:** Use a clearly labelled synthetic event to test a detection path end to end.

## 3. Check the event reached Sentinel

Mode: read-only

Back in the presenter terminal, run the commands. They look up the Sentinel workspace's own GUID (the monitoring workspace from the Observe demo is a different workspace) and query its Event table for the training marker from the last hour. Match the computer, the marker text and a recent timestamp before opening any incident.

```powershell
$SentinelWorkspaceId = az resource show --ids $Demo.SentinelWorkspaceResourceId --query properties.customerId -o tsv
if ($LASTEXITCODE -ne 0 -or -not $SentinelWorkspaceId) { throw 'Cannot resolve the Sentinel workspace customer GUID.' }
$q = "Event | where TimeGenerated > ago(1h) | where Source == 'CAS26Demo' and EventID == 2601 | where RenderedDescription has 'CAS26 Sentinel training' | project TimeGenerated,Computer,RenderedDescription"
az monitor log-analytics query --workspace $SentinelWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** At least one row from cas26-arcwin01 with the text CAS26 Sentinel training and a recent TimeGenerated.

**If this fails:** If no event appears, check in this order: the event on the guest (Event Viewer > Application), the Application-log DCR and its DCR association, the workspace the DCR sends to, and ingestion delay. SecurityEvent is a different table; do not switch tables to get rows.

**Speaker explanation:** Say: the Sentinel slide in practice. The server's events come in through the same agent and data collection rule we saw in Observe. Data first; then the rule runs over it.

**Attendee takeaway:** A scheduled detection depends on the right data reaching the right workspace; the analytics rule cannot compensate for missing collection.

## 4. Find the incident

Mode: read-only

Run the query; it lists the latest state of each CAS26 TRAINING incident from the last 24 hours. Then open Incidents in the portal, filter on CAS26 TRAINING and open the newest one. The portal queue is where you work; the query is corroboration.

```powershell
$SentinelWorkspaceId = az resource show --ids $Demo.SentinelWorkspaceResourceId --query properties.customerId -o tsv
if (-not $SentinelWorkspaceId) { throw 'Could not resolve the Sentinel workspace customer GUID.' }
$q = "SecurityIncident | where TimeGenerated > ago(24h) | summarize arg_max(TimeGenerated, *) by IncidentName | where Title startswith 'CAS26 TRAINING' | project IncidentNumber,Title,Severity,Status,Owner,CreatedTime"
az monitor log-analytics query --workspace $SentinelWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** One or more CAS26 TRAINING incidents with number, severity, status and created time, and the same incident in the portal queue, linked to the training rule.

**If this fails:** If SecurityIncident is unavailable, inspect the configured Sentinel incident queue. No incident may mean ingestion, rule scheduling, suppression/grouping or incident creation settings need checking; do not create a false screenshot.

**Speaker explanation:** Say: the rule found the marker and raised an incident. An incident is a case for a person to own, not an alarm to silence.

**Attendee takeaway:** A detection turns data into an incident; the incident queue is where an analyst takes ownership.

## 5. Follow the evidence and entities

Mode: portal

In the incident, open the timeline, the alert and the underlying event. Match the computer (cas26-arcwin01), source and event ID, message and timestamps. Open the investigation graph only if the rule maps entities; missing entities are a rule-design gap, not an invisible successful investigation.

**Expected evidence:** The incident is connected to the actual harmless event from cas26-arcwin01, with matching times.

**If this fails:** Confirm table/connector permissions and time zones. An incident title alone does not prove the end-to-end data path.

**Speaker explanation:** Say: read what was actually observed: this server, this event, this time. Anything beyond that is the analyst's hypothesis.

**Attendee takeaway:** The incident is connected to an actual harmless event from the selected guest.

## 6. Record the owner and the decision

Mode: portal

Assign the prepared training owner (if this account may) and add a short comment: the signal is a benign CAS26 exercise, and here is what was verified. Do not run playbooks or containment against real hosts.

**Expected evidence:** Only the training incident is updated; ownership and a reasoned response are preserved in its history.

**If this fails:** If incident-write access is intentionally unavailable, show existing ownership and state the intended action. Do not elevate access during the talk.

**Speaker explanation:** Say: every incident needs an owner and a written decision, even a training one.

**Attendee takeaway:** Record who owns an incident and why it was decided in the incident itself, so its history explains the outcome.

## 7. Close the exercise without hiding history

Mode: portal

If the exercise calls for closure, close only this training incident with a benign/training classification and a comment. Show the recorded status. Transition to section 3, Govern: which team owns it, and does it stay the way we agreed?

**Expected evidence:** The training record retains its investigation/decision history; no claim of containing a real attack is made.

**If this fails:** If this account may not close incidents, leave it assigned with its comment and say so; never raise permissions on stage.

**Speaker explanation:** Bridge: the data path and the response depended on things set up in advance: the workspace, the roles, collection and the rule. Keeping that set-up consistent across every estate is governance. Transition: section 3, Govern.

**Attendee takeaway:** Sentinel incident handling depends on configured data sources, analytics and entity mapping. An incident is evidence requiring interpretation; it is not proof that a threat has been contained.

## Reset and verification

Close/comment only the identified training incident according to the exercise contract. Keep rule and collection configuration for the next session. Do not delete incident history or disable a shared rule.

## If the live demo fails

If ingestion or the incident queue is slow, show the rehearsal capture of event, rule and incident with workspace and timestamps, and name the step you would have run.

## Timing and handoff

Event ingestion plus the scheduled rule can take several minutes. Generate and verify the training event before the session and open the incident it created, rather than waiting for a new incident live.
