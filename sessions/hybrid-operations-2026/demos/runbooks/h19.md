# H19 — Prove access to an Arc resource with Azure RBAC

Slide 31 · Rehearsal target: 2.5 minutes

What this demo shows and why: being able to see a server in Azure and being allowed to change it are different permissions. Two real accounts try the same small, reversible change (adding a tag) on the same Arc-enabled server: the read-only account is refused, the operator account succeeds, and the Azure Activity Log records who did what. This is the Azure door from the four-doors slide and the people rule from the three-rules slide: read-only by default, change rights only through an approved, scoped role.

## Before delivery

- Names used in this runbook: iic-cas26-prd-web-01 is an AWS EC2 server of the sample application, Arc-enabled through the connector (Ec2RbacArcResourceId); cas26-test-* are cloud-only test users and sg-tplabs-cas26-* the security groups that hold their roles; CAS26RbacProof is a tag reserved for this demo.
- To reproduce: one Arc-enabled server, two accounts (one with Reader, one with a narrow role that can write tags, such as Tag Contributor, at the resource group or on the machine), and two terminals signed in separately (give each its own AZURE_CONFIG_DIR).
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: check inherited assignments, group memberships and active PIM roles for both accounts; a Reader assignment does not cancel a broader inherited role. Pre-stage the role assignments; never grant broad permissions during the demo.
- Presenter lab: use two already-authenticated terminal and browser profiles with distinct AZURE_CONFIG_DIR values. Do not swap tokens or simulate roles.
- Presenter lab: CAS26RbacProof goes on iic-cas26-prd-web-01 only, never on the Policy demo's target (iic-cas26-prd-api-01), so rehearsal tag writes cannot disturb that demo's before-state. It changes the Azure tag only, never the native AWS instance tag. Record whether the tag exists before the demo. The Owner-tag policy touches only the Owner tag, so CAS26RbacProof has no policy side effect.
- Presenter lab: choose the reader and operator from the cas26-test-* users and the sg-tplabs-cas26-* groups, and verify their role assignments at the AWS_<AccountId> resource group or on the exact machine.

## 1. Show the two accounts

Mode: read-only

In each of the two terminals (reader first, then operator), load context and show the signed-in account. In the portal, open the machine > Access control (IAM) > Check access and look up each account to show its effective roles, including anything inherited from the resource group or a group membership.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
az account show --query '{principal:user.name,type:user.type,tenant:tenantId,subscription:id}' -o json
```

**Expected evidence:** Two different user names on the same tenant and subscription; Check access shows Reader for the reader and the scoped tag-writing role for the operator.

**If this fails:** If both terminals show the same user, AZURE_CONFIG_DIR is not separate: stop and fix it before any write. If Check access shows a broader inherited role for the reader, the refusal in step 3 will not happen; say so and use the rehearsal capture.

**Speaker explanation:** Say: of the four doors into a server, this demo tests only the Azure door, whose key is an Azure role. And it shows the people rule live: read-only by default, change rights only through an approved, scoped role (in production, activated through PIM for a limited time after MFA).

**Attendee takeaway:** Check effective access, including inherited and group roles, not only the assignment you expect.

## 2. The reader can see the server

Mode: read-only

In the reader terminal, read the EC2 Arc machine and its tags. Note whether CAS26RbacProof is already present: that is the baseline to restore in step 6 (normally it is absent).

```powershell
az resource show --ids $Demo.Ec2RbacArcResourceId --query '{id:id,tags:tags,identity:identity}' -o json
```

**Expected evidence:** The read succeeds and shows the machine ID, its tags (normally without CAS26RbacProof) and its managed identity.

**If this fails:** If the read fails, the reader lacks Reader at this scope or the terminal is on the wrong subscription; check step 1 and show the rehearsal capture.

**Speaker explanation:** Say: the reader can see everything about this server in Azure. That key opens the Azure door only: it does not let anyone sign in to the server, stop the VM in AWS, or read the application's data.

**Attendee takeaway:** Reader access is visibility only; it does not open the sign-in, hosting or application doors.

## 3. The reader tries a change and is refused

Mode: change

Still in the reader terminal, run the tag update. This is a real write request that is expected to be refused; the script stops if the write unexpectedly succeeds. Read the error aloud: AuthorizationFailed, naming the account, the action (Microsoft.Resources/tags/write) and the scope.

```powershell
az tag update --resource-id $Demo.Ec2RbacArcResourceId --operation Merge --tags CAS26RbacProof=operator-verified
$ReaderWriteExitCode = $LASTEXITCODE
if ($ReaderWriteExitCode -eq 0) { throw 'Unexpected write success: stop, inspect effective privileges, and restore the reserved tag.' }
# Inspect the actual error: AuthorizationFailed is expected; network/CLI errors do not prove RBAC denial.
```

**Expected evidence:** An AuthorizationFailed error naming the reader account, the tags write action and the machine's scope; the script does not throw.

**If this fails:** A network or CLI error is not a refusal and proves nothing about access: fix it and rerun, or show the capture. If the update succeeds, the reader has more rights than intended: stop, find the inherited, group or PIM role, keep the honest result, and restore the tag as in step 6.

**Speaker explanation:** Say: same server, same command, and Azure says no, and says exactly why: this account, this action, this scope.

**Attendee takeaway:** A real refused request, with its error, proves a permission boundary; a hidden button in the portal does not.

## 4. The operator makes the same change

Mode: change

In the operator terminal, run exactly the same tag update; the second command reads the tags back. No role is created or widened on stage.

```powershell
az tag update --resource-id $Demo.Ec2RbacArcResourceId --operation Merge --tags CAS26RbacProof=operator-verified
if ($LASTEXITCODE -ne 0) { throw 'The operation failed. Stop and follow the recovery instructions.' }
az resource show --ids $Demo.Ec2RbacArcResourceId --query tags -o json
```

**Expected evidence:** The update succeeds and the tags now include CAS26RbacProof=operator-verified; every other tag is unchanged.

**If this fails:** If a deny assignment or policy blocks the action, explain the additional boundary. Do not disable it to make the demonstration work.

**Speaker explanation:** Say: the only difference is the account and its role. The operator holds a narrow role that can write tags, at this scope only.

**Attendee takeaway:** Change rights come from a scoped role on the right account, not from being an administrator everywhere.

## 5. Who did what: the Activity Log

Mode: read-only

Run the Activity Log query for the last hour (or open the machine > Activity log in the portal). Find the tag write and read its time, caller, operation, status and correlation ID.

```powershell
az monitor activity-log list --resource-id $Demo.Ec2RbacArcResourceId --offset 1h --query '[].{time:eventTimestamp,caller:caller,operation:operationName.value,status:status.value,correlation:correlationId}' -o table
```

**Expected evidence:** A successful tag write whose caller is the operator account, at the time of step 4. The refused attempt may also appear as a failed write; if it has not arrived yet, the CLI error from step 3 is the evidence.

**If this fails:** Activity Log can lag; do not infer caller from the currently open portal session. Read the recorded caller and correlation ID.

**Speaker explanation:** Say: every control-plane change is recorded with who made it. That record is what an auditor asks for.

**Attendee takeaway:** The Azure Activity Log records who changed what and when; it is the evidence of an authorized change.

## 6. Put the tag back and close

Mode: change

In the operator terminal, restore the baseline recorded in step 2. Normally CAS26RbacProof was absent, so run the commands below: they remove only that key and read the tags again. If it had an earlier value, set that value back in the portal (machine > Tags) instead. Close on the trap from the four-doors slide.

```powershell
# Normal case: CAS26RbacProof did not exist before the demo, so remove only that key.
az tag update --resource-id $Demo.Ec2RbacArcResourceId --operation Delete --tags CAS26RbacProof=operator-verified
if ($LASTEXITCODE -ne 0) { throw 'Tag restore failed: remove CAS26RbacProof in the portal (machine > Tags) before moving on.' }
az resource show --ids $Demo.Ec2RbacArcResourceId --query tags -o json
```

**Expected evidence:** CAS26RbacProof is gone (or back to its recorded value), every other tag is unchanged, and no temporary broad role exists. Management permission is distinguished from signing in to the server.

**If this fails:** If the delete fails, remove CAS26RbacProof in the portal (machine > Tags) as the operator before moving on; never leave the reserved tag behind for the next session.

**Speaker explanation:** Close on the trap: an Azure role that can run commands or install extensions is admin access inside the server, so hand it out like server admin. Debrief: account, role, scope, allowed action, refused action and the Activity Log record. That was the people rule; the fix-up tools rule returns in the Policy demo, whose remediation identity can change tags in one resource group only. Transition: knowing who can act does not tell us what is weak or under attack; that is Defender for Cloud.

**Attendee takeaway:** RBAC evaluates effective access from all applicable assignments. Four doors, four keys: an Azure role opens the Azure door only, and reader visibility, management rights and guest sign-in are related but distinct security decisions.

## Reset and verification

Restore only the reserved tag from the recorded baseline; preserve activity history. Remove temporary CAS26 role assignments only if separately created for preparation and after verifying no other session depends on them. Keep prepared identities for rehearsals.

## If the live demo fails

If sign-in or the portal is slow, show the rehearsal capture from the two real principals (the denial, the successful write and the Activity Log entries) and name the step you would have run. Never emulate a denial with fabricated output.

## Timing and handoff

Role and PIM changes and Activity Log ingestion take time to appear; activate and check access beforehand. Never grant a broader role to get around a propagation delay.
