# H24 — Evaluate and remediate Arc machines with Azure Policy — on-premises, then AWS

Slide 42 · Rehearsal target: 5 minutes

What this demo shows and why: this runs the Require-an-Owner-tag policy from the two Azure Policy slides (39 and 40) on two real Arc-enabled servers: first the on-premises server connected in the first demo, then an AWS EC2 server onboarded by the connector. For each we walk the boxes of 'How Azure Policy works': definition and assignment, an evaluation that finds the Owner tag missing (NonCompliant), a remediation task in which the Modify effect adds the tag, and a fresh check that agrees. Same policy, same steps, two hosting locations.

## Before delivery

- Names used in this runbook: cas26-arcwin01 is the on-premises Windows server (pass 1); iic-cas26-prd-api-01 is an AWS EC2 server of the sample application (pass 2). tplabs-cas26-require-owner-tag-modify is the policy assignment on the operations resource group rg-tplabs-cas26-ops-eus-01; cas26-modify-owner-tag-aws-arc is the policy definition assigned separately on the connector-created AWS_<AccountId> resource group. Both add a missing Owner tag with the Modify effect.
- To reproduce: a policy that adds a missing Owner tag with the Modify effect (the built-in 'Add a tag to resources' works), assigned at your resource group with a system-assigned managed identity that holds Tag Contributor there, and enforcement mode DoNotEnforce so the missing tag stays visible until you remediate (step 3 explains why). You need Resource Policy Contributor to create remediation tasks, and Azure CLI with the resource-graph extension.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab, pass 1: cas26-arcwin01 (OnPremArcResourceId) was connected in the first demo with Event=cas26 and no Owner tag, so the operations-resource-group assignment (PolicyAssignmentId) evaluates it NonCompliant. Record its tags before the demo.
- Presenter lab, pass 2: iic-cas26-prd-api-01 (Ec2ArcResourceId) under the AWS-resource-group assignment of cas26-modify-owner-tag-aws-arc (Ec2PolicyAssignmentId). The operations assignment cannot reach the connector-created resource group, and its Event=cas26 filter never matches connector-created machines, so the second assignment is required; it allowlists the six IIC application machines by exact name, so every other machine in that group is outside its scope.
- Presenter lab: verify both assignments and the definition: scope, enforcementMode=DoNotEnforce, parameters and defaults (tagValue may come from the definition default), exclusions, managed identity and its Tag Contributor role at the exact scope. DoNotEnforce is deliberate: in Default mode the Arc agents' routine status writes fire the Modify effect and tag every matching machine within seconds, leaving nothing to remediate. Do not switch either assignment to Default before the session.
- Presenter lab: never remove a genuine owner tag to stage noncompliance. Between rehearsals reset by deleting the Owner tag on the Arc resource only (az tag update --operation Delete); rehearse on a dev EC2 machine and keep iic-cas26-prd-api-01 for delivery.
- Presenter lab: a native AWS tag is separate from the Arc resource's Owner tag; pass 2 changes Azure metadata only. Do not use the RBAC demo's machine (Ec2RbacArcResourceId) in this demo.

## 1. Pass 1: the on-premises server, before

Mode: read-only

Load context and set the two variables for pass 1: the target is cas26-arcwin01 and the assignment is the operations resource group's Owner-tag assignment. Run the resource read and point at the tags: Event=cas26 is there, Owner is not. Nothing was removed to stage this; the server was connected without an Owner tag in the first demo.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
$TargetId = $Demo.OnPremArcResourceId
$AssignmentId = $Demo.PolicyAssignmentId
az resource show --ids $TargetId --query '{id:id,type:type,tags:tags,properties:properties}' -o json
```

**Expected evidence:** The Microsoft.HybridCompute/machines resource for cas26-arcwin01, with tags that include Event=cas26 and no Owner tag.

**If this fails:** If an Owner tag is already present, a rehearsal left it: say so, show the task history from that rehearsal instead of deleting the tag live, and go to pass 2. If the read fails, check OnPremArcResourceId in demo.local.json.

**Speaker explanation:** Say: the same server we connected at the start; now we manage it. This is the running example from the Policy slides, the Require-an-Owner-tag policy, and this server has no Owner tag.

**Attendee takeaway:** Record a resource's tags before a governance change so you can prove what changed.

## 2. Read the definition and the assignment

Mode: read-only

Run the commands. The first prints the assignment: its scope (the operations resource group), enforcement mode (DoNotEnforce), parameters and managed identity. The second prints the definition it points to: the rule 'if the Owner tag is missing, Modify adds it', and the default tag value. Point out that the assignment sets no tag value, so the definition's default decides it. The policy adds a missing Owner tag; it does not repair an empty or wrong one.

```powershell
$assignment = az rest --method get --url ($AssignmentId + '?api-version=2022-06-01') | ConvertFrom-Json
$assignment | ConvertTo-Json -Depth 20
$definition = az rest --method get --url ($assignment.properties.policyDefinitionId + '?api-version=2023-04-01') | ConvertFrom-Json
$definition | ConvertTo-Json -Depth 20
```

**Expected evidence:** Assignment scope = the operations resource group, enforcementMode = DoNotEnforce, a SystemAssigned identity; the definition has a Modify effect that adds the Owner tag and a default value that is a placeholder, not a real owner.

**If this fails:** If the ID is an initiative, select its exact definition reference before proceeding. Do not run the standalone-policy command unchanged. If resolved value is a placeholder, describe placeholder compliance; do not claim it equals the configured ExpectedOwner.

**Speaker explanation:** Say: the first two boxes on the 'How Azure Policy works' slide. The definition is the rule; the assignment says where it applies. And the default value it writes is a placeholder, not a person.

**Attendee takeaway:** Read the assignment and the definition together: default parameter values decide the outcome when the assignment is silent.

## 3. Who may fix it, and why it is still NonCompliant

Mode: read-only

In the portal, open Policy > Assignments > the assignment > Managed identity, and its role assignments: Tag Contributor on the operations resource group only. Then run the compliance query for this one server and this one assignment and read the state and timestamp. Explain why it is still NonCompliant: the assignment runs in DoNotEnforce, so the server's routine status updates did not trigger the Modify effect (in Default mode it would have been tagged within seconds, leaving nothing to show).

```powershell
az policy state list --resource $TargetId --filter "PolicyAssignmentId eq '$AssignmentId'" --query '[].{state:complianceState,time:timestamp,assignment:policyAssignmentId,definition:policyDefinitionId,resource:resourceId}' -o table
```

**Expected evidence:** One row: complianceState NonCompliant, with a timestamp, this assignment and this server; the remediation identity can write tags at this scope.

**If this fails:** No row is not compliance. Wait for evaluation in preparation. ExistingNonCompliant needs an evaluated noncompliant result; do not broaden the resource selection. If already compliant, inspect prior evidence rather than deleting a tag live.

**Speaker explanation:** Say: the middle boxes: evaluate, then NonCompliant, and the reason is the missing Owner tag. The fix will run as the assignment's own identity, which can change tags in this one resource group and nothing else. That is the fix-up tools rule from the three rules.

**Attendee takeaway:** A current applicable NonCompliant row identifies a genuinely absent tag, and the remediation identity can perform the rule's operation.

## 4. Run one remediation task: Modify adds the tag

Mode: change

Create a remediation task for this one server under this one assignment; the name includes the time so it is unique. The task fixes only resources already evaluated as NonCompliant. No name filter, resource-group-wide remediation or re-evaluation discovery is used.

```powershell
$RemediationName = 'cas26-onprem-' + (Get-Date -Format 'yyyyMMddHHmmss')
az policy remediation create --resource $TargetId --policy-assignment $AssignmentId --name $RemediationName --resource-discovery-mode ExistingNonCompliant -o json
if ($LASTEXITCODE -ne 0) { throw 'The operation failed. Stop and follow the recovery instructions.' }
```

**Expected evidence:** JSON for the new task with this assignment, this server and provisioningState Accepted or Evaluating. Accepted is not done.

**If this fails:** If permission or evaluation fails, retain the error and use genuine before/after evidence. Do not assign broader permissions or change effect/definition during the demo.

**Speaker explanation:** Say: the remediation task box. One task, one server, one assignment, running as the assignment's identity.

**Attendee takeaway:** The task targets the selected resource under the selected assignment; acceptance of the request is not completion.

## 5. Check the task and read the tag

Mode: read-only

Run the commands: the task's status, then the server's tags read straight from the resource. Compare the Owner value with the definition default from step 2 and with ExpectedOwner in demo.local.json.

```powershell
az policy remediation show --resource $TargetId --name $RemediationName -o json
az resource show --ids $TargetId --query '{id:id,tags:tags}' -o json
```

**Expected evidence:** The task shows Succeeded with the resource remediated; the tags now include Owner with the governed value, and every other tag is unchanged.

**If this fails:** A task can have zero remediated resources or failures. Read counts/errors. Policy compliance may lag the direct resource read.

**Speaker explanation:** Say: the tag is there. That proves the control works. It does not prove a person has accepted ownership; the placeholder value makes that gap visible.

**Attendee takeaway:** Task result and actual resource property agree; unrelated tags remain unchanged.

## 6. Pass 1 result: a fresh check agrees

Mode: read-only

Run the Resource Graph read and the compliance query again and compare the timestamp with step 3. If the new evaluation has not arrived yet, say 'evaluation pending' and rely on the tag readback from step 5. Then go straight to pass 2 in the same terminal.

```powershell
az graph query --subscriptions $Demo.SubscriptionId -q "Resources | where id =~ '$TargetId' | project id,name,tags" -o json
az policy state list --resource $TargetId --filter "PolicyAssignmentId eq '$AssignmentId'" --query '[].{state:complianceState,time:timestamp,resource:resourceId}' -o table
```

**Expected evidence:** Resource Graph shows the Owner tag; the compliance row shows Compliant with a newer timestamp, or still the old row while re-evaluation is pending. Do not announce Compliant until the timestamp supports it.

**If this fails:** ARG and Policy are eventually consistent. Preserve direct read evidence and explicitly say reevaluation pending if that is the result.

**Speaker explanation:** Say: the last box on the slide: after the fix, a fresh check agrees. Read the timestamp before you say Compliant.

**Attendee takeaway:** Changed Azure resource state and a fresh policy evaluation are distinct evidence. Do not announce fresh compliance until the timestamp supports it.

## 7. Pass 2: switch to the AWS server

Mode: read-only

Change only the two variables. The command block reads the EC2 Arc machine in the connector-created resource group and its compliance under the AWS-resource-group assignment: same definition, an allowlist of the six IIC application machines, DoNotEnforce, its own identity with Tag Contributor on that group. State the boundary: the Owner tag here is Azure metadata; the EC2 instance's own AWS tags and lifecycle are unchanged.

```powershell
$TargetId = $Demo.Ec2ArcResourceId
$AssignmentId = $Demo.Ec2PolicyAssignmentId
az resource show --ids $TargetId --query '{id:id,type:type,tags:tags,status:properties.status}' -o json
az policy state list --resource $TargetId --filter "PolicyAssignmentId eq '$AssignmentId'" --query '[].{state:complianceState,time:timestamp,resource:resourceId}' -o table
```

**Expected evidence:** The EC2 Arc machine (the one whose AWS instance ID the connector demo mapped), no Owner tag, and a NonCompliant row under the AWS-resource-group assignment.

**If this fails:** If the compliance row is missing, the assignment has not evaluated yet: during preparation run az policy state trigger-scan --resource-group $Demo.AwsResourceGroup (it takes minutes); on stage, show the missing tag as the before evidence and say evaluation is pending. If the row says Compliant, the tag was re-applied: check that enforcementMode is DoNotEnforce and reset before delivery (see Reset).

**Speaker explanation:** Say: now an AWS server, onboarded by the connector earlier. Only two things change: the target and the assignment. A second assignment exists because the first is scoped to a different resource group and filters on the Event=cas26 tag, which connector-created machines do not carry. The Owner tag lives on the Azure resource; the EC2 instance's own AWS tags do not change.

**Attendee takeaway:** The same governance control applies to an AWS server through its Azure Arc representation; a second assignment is needed only because scope and tag filters differ, not because the mechanism differs.

## 8. Pass 2 result: remediate the AWS server and verify

Mode: change

Run the block: the same remediation, task status, tag readback and compliance check against the EC2 target. Compare the two passes aloud: same definition, same identity model, same evidence, different hosting location and resource group.

```powershell
$RemediationName = 'cas26-ec2-' + (Get-Date -Format 'yyyyMMddHHmmss')
az policy remediation create --resource $TargetId --policy-assignment $AssignmentId --name $RemediationName --resource-discovery-mode ExistingNonCompliant -o json
if ($LASTEXITCODE -ne 0) { throw 'The operation failed. Stop and follow the recovery instructions.' }
az policy remediation show --resource $TargetId --name $RemediationName --query '{state:provisioningState,deployed:deploymentStatus}' -o json
az resource show --ids $TargetId --query tags -o json
az policy state list --resource $TargetId --filter "PolicyAssignmentId eq '$AssignmentId'" --query '[].{state:complianceState,time:timestamp}' -o table
```

**Expected evidence:** The remediation task succeeds, the Owner tag is present on the EC2 Arc representation with the governed value, unrelated tags are unchanged, and the next Policy evaluation reports Compliant with a fresh timestamp.

**If this fails:** A remediation failure with an authorization error means the assignment identity lacks Tag Contributor at the AWS resource group: re-run shared/foundation/scripts/Ensure-Cas26AwsArcOwnerTagGovernance.ps1 in plan mode to confirm the grant. A pending compliance row is normal for several minutes; show the tag readback as the resource evidence.

**Speaker explanation:** Say: same policy, same steps, two hosting locations. The tag proves the control works, not that a human accepted ownership. Transition: what the Policy demo proved.

**Attendee takeaway:** One procedure governed an on-premises guest and an AWS server. The evidence to keep is the same for both: exact IDs, acting identity, before/after tag, task result and the fresh evaluation timestamp.

## Reset and verification

Keep the corrected tags for the next session. Between rehearsals delete only the Owner tag on the demonstrated Arc representations; because both assignments are DoNotEnforce the tag stays absent until the next remediation task. Never disable Policy or remove a genuine owner. Retain task history; removing a task is not undoing its tag change. No native AWS tags, EC2 lifecycle or connector settings are changed.

## If the live demo fails

If a remediation task or evaluation is slow, read the tag directly from the resource, show the rehearsal capture of the completed task and fresh evaluation for that pass, and name the step you would have run. Never present a second AWS machine as the on-premises guest.

## Timing and handoff

Remediation and the following Policy and Resource Graph refresh are separate asynchronous stages in each pass. Do not loop until green: read the resource, note the evaluation timestamp and move on.
