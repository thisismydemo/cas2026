# H16 — Query the estate, then read machine and service health

Slide 27 · Rehearsal target: 3.5 minutes

What this demo shows and why: two questions need two different places to ask. Azure Resource Graph answers 'what exists and how is it configured' right now; Log Analytics answers 'what happened over time', using data the Azure Monitor agent sends under a data collection rule (DCR). We then place one real order in the sample application and read machine health and service health side by side, because green servers do not prove that customers' orders complete.

## Before delivery

- Names used in this runbook: IIC Hybrid Orders is the session's sample application; each order passes through Azure, an on-premises worker and an AWS worker. Cas26Service_CL is the custom Log Analytics table where each order writes one row per stage. dcr-tplabs-cas26-linux-eus-01 is the data collection rule (DCR) for the Linux machines; dcr-cas26-requests-eus-01 is the DCR that receives the order records. hm-tplabs-cas26-service-cus-01 is the Azure Monitor health model for the service. cas26-arcwin01 and cas26-lnx01 are the on-premises Arc machines.
- To reproduce: Arc-enabled machines with the Azure Monitor agent and a DCR association to a Log Analytics workspace, Reader on the subscription and Log Analytics Reader on the workspace, and Azure CLI with the resource-graph, connectedmachine and log-analytics extensions. The order and health-model steps need an application of your own that writes one record per request.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: prepare browser tabs for Resource Graph Explorer, Log Analytics (Logs), the CAS26 service-operations workbook and the health model; check each tab's scope, workspace and time range beforehand.
- The configured LogAnalyticsWorkspaceId is the workspace/customer GUID used by az monitor log-analytics query. It is distinct from the Sentinel workspace ARM resource ID and from an Azure Monitor workspace.
- Presenter lab: machine evidence uses one of the EC2 Arc machines (Ec2ArcResourceId); the same queries work for the on-premises machines. ServiceUrl is the IIC order endpoint and HealthModelResourceId the health model. Place one rehearsal order and confirm its stage rows arrive in Cas26Service_CL.

## 1. Ask Resource Graph what exists

Mode: read-only

Load context, then run the Resource Graph query (the same query can be pasted into Resource Graph Explorer in the portal). It lists Arc machines, Azure VMs and Arc-enabled Kubernetes clusters in the operations and AWS resource groups of the selected subscription.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
$query = "Resources | where resourceGroup in~ ('$($Demo.OperationsResourceGroup)', '$($Demo.AwsResourceGroup)') | where type in~ ('microsoft.hybridcompute/machines','microsoft.compute/virtualmachines','microsoft.kubernetes/connectedclusters') | project name,type,resourceGroup,id,tags"
az graph query --subscriptions $Demo.SubscriptionId -q $query -o table
```

**Expected evidence:** The on-premises Arc machines (including cas26-arcwin01 and cas26-lnx01) in the operations resource group; the eight EC2 Arc machines and the EKS connected cluster in the AWS resource group; each with type, resource group, ID and tags. This is current configuration, not history.

**If this fails:** If the table is empty, confirm the subscription (az account show) and that OperationsResourceGroup and AwsResourceGroup in demo.local.json match the portal. Do not remove the resource-group filter just to get rows.

**Speaker explanation:** Say: the first place to ask is Resource Graph: what exists right now and how it is configured, across Azure, our datacenter and AWS. It cannot tell us whether anything worked five minutes ago.

**Attendee takeaway:** Resource Graph answers inventory and configuration questions across every estate; it holds no history of performance or requests.

## 2. Check the machine is set up to send data

Mode: read-only

Run the two commands for the selected EC2 Arc machine: its resource, then its extensions. In the portal, open the same machine > Extensions and show AzureMonitorLinuxAgent; then open Monitor > Data Collection Rules > dcr-tplabs-cas26-linux-eus-01 > Resources and show this machine in the rule's DCR associations.

```powershell
az resource show --ids $Demo.Ec2ArcResourceId --query '{id:id,identity:identity,tags:tags,properties:properties}' -o json
az connectedmachine extension list --machine-name ($Demo.Ec2ArcResourceId.Split('/')[-1]) --resource-group $Demo.AwsResourceGroup --query '[].{name:name,state:properties.provisioningState}' -o table
```

**Expected evidence:** The extension list includes AzureMonitorLinuxAgent in state Succeeded, and the machine is listed under dcr-tplabs-cas26-linux-eus-01's resources.

**If this fails:** If the agent or the DCR association is missing, say so: that is the first thing to check when a chart is empty. Do not show another machine's evidence instead.

**Speaker explanation:** Say: slide 23 in practice. The agent is installed, the data collection rule says what to collect and where to send it, and the DCR association assigns that rule to this server. That is set-up, not proof that data is arriving.

**Attendee takeaway:** Agent plus DCR association is the set-up; only fresh data in the workspace proves collection works.

## 3. Ask Log Analytics when the machine last reported

Mode: read-only

Run the two KQL queries through the CLI (or paste them into Logs in the workspace). The first reads the newest Heartbeat row for this exact machine; the second counts CPU samples from the last 30 minutes. Compare LastSeen with the current UTC time.

```powershell
$q = "Heartbeat | where TimeGenerated > ago(30m) | where _ResourceId =~ '$($Demo.Ec2ArcResourceId)' | summarize LastSeen=max(TimeGenerated) by Computer, _ResourceId"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
$q = "Perf | where TimeGenerated > ago(30m) | where _ResourceId =~ '$($Demo.Ec2ArcResourceId)' | where ObjectName == 'Processor' and CounterName == '% Processor Time' | summarize Samples=count(), LastSeen=max(TimeGenerated), AvgCpu=avg(CounterValue)"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** A Heartbeat LastSeen within the last few minutes, and a non-zero Samples count with a recent LastSeen for Perf. No rows means missing, stale or uncollected evidence, not a healthy machine.

**If this fails:** Check, in order: the workspace GUID, the DCR association, agent health, table permissions and the time window. Never widen the query to the whole estate and call someone else's heartbeat proof.

**Speaker explanation:** Say: the second place to ask is Log Analytics: what happened over time. This machine sent a heartbeat moments ago and CPU samples in the last half hour. That is machine health, and it is still not what the customer sees.

**Attendee takeaway:** Heartbeat and performance data prove the machine is reporting; an empty result is missing evidence, not good news.

## 4. Place one real order

Mode: read-only

Run the order client. It places one demo-tagged order in IIC Hybrid Orders and prints its CorrelationId (the ID that follows the order through every stage), which copy of the portal served it (Origin: Azure or AWS), its overall status and the result of every stage. The first line stops the step if ServiceUrl is still a placeholder.

```powershell
if ($Demo.ServiceUrl -match '^PENDING|REPLACE_WITH') { throw 'Populate ServiceUrl in demo.local.json with the IIC order endpoint before delivery.' }
$order = & ./sessions/hybrid-operations-2026/demos/scripts/Invoke-Cas26Request.ps1 -BaseUri $Demo.ServiceUrl -DemoTag
$order | Select-Object CorrelationId, OrderNumber, Origin, Status, ElapsedMs
$order.Stages | Format-Table Cloud, Component, Stage, Success, DurationMs
```

**Expected evidence:** Status Completed with a CorrelationId and an Origin, and a stage table in which every stage in Azure, on-premises and AWS shows Success True with its duration. A portal that loads is not an order that completed.

**If this fails:** A failed stage can be a configured demo fault; check FailureMode before calling it an incident. A timeout may indicate a stuck queue or a missing worker. Preserve the actual response; do not manufacture a successful order.

**Speaker explanation:** Say: slide 24, green servers, broken service. The only thing that proves the service works is a real order finishing. This one went through Azure, our datacenter and AWS.

**Attendee takeaway:** A completed request is the proof of service health; a portal that loads is not.

## 5. Read order outcomes in the logs

Mode: read-only

Run the queries. The first summarizes all IIC orders from the last 30 minutes: each order writes one row per stage, so rows are grouped by CorrelationId before counting orders, failed orders and unresolved orders. The second shows only the order from step 4, stage by stage, across the three clouds. Zero orders in the window means not enough evidence, not 0% failure.

```powershell
$q = "Cas26Service_CL | where TimeGenerated > ago(30m) | where Customer == 'IIC' | summarize Completed=countif(Component == 'Coordinator' and Stage == 'Completed' and Success == true), Failed=countif(Success == false), LastSeen=max(TimeGenerated) by CorrelationId | summarize Orders=count(), FailedOrders=countif(Failed > 0), Unresolved=countif(Completed == 0 and Failed == 0), LastSeen=max(LastSeen) | extend FailurePercent=iff(Orders > 0, 100.0*FailedOrders/Orders, real(null))"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
if (Get-Variable order -ErrorAction SilentlyContinue) {
    $q = "Cas26Service_CL | where CorrelationId == '$($order.CorrelationId)' | project TimeGenerated, Cloud, Component, Stage, Success, DurationMs, FailureMode | order by TimeGenerated asc"
    az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
}
```

**Expected evidence:** Orders, FailedOrders, Unresolved, LastSeen and FailurePercent for the window; then the step 4 order's stage rows, once ingested (usually within a few minutes).

**If this fails:** If the new order's rows have not arrived yet, say so and use the client output from step 4; ingestion delay is not a failure. sessions/hybrid-operations-2026/demos/src/queries/service-overview.kql is the same order summary, ready to paste into the Logs blade.

**Speaker explanation:** Say: the same order, now as evidence in the logs, one row per stage in each cloud. If it is not here yet, that is ingestion delay; the client output from step 4 already proved the order.

**Attendee takeaway:** Summarize per request before you count; stage-level rows otherwise overstate the number of orders.

## 6. Read machine health and service health together

Mode: read-only

Open the CAS26 service-operations workbook, then the health model hm-tplabs-cas26-service-cus-01 in the portal. For each workbook panel, name where its data comes from: Resource Graph (configuration), Log Analytics KQL (logs), platform metrics, or Azure Monitor workspace PromQL. In the health model, follow the rollup from slide 25: the customer order depends on Azure coordination, on-premises validation and AWS fulfillment; read each part's state and how fresh its evidence is, then who owns the next action and what would prove recovery. Run the command only to confirm you are on the right health model resource; health itself is read in the portal view. Mention once that the Whole-Service Observability session builds this model in depth. Transition to section 2, Secure.

```powershell
if ($Demo.HealthModelResourceId -match '^PENDING|REPLACE_WITH') { throw 'Populate HealthModelResourceId in demo.local.json before delivery.' }
az resource show --ids $Demo.HealthModelResourceId --query '{id:id,location:location,provisioning:properties.provisioningState}' -o json
```

**Expected evidence:** The audience can distinguish current metadata, machine condition and customer outcome. provisioning=Succeeded is deployment status, not health; health state is read in the Health Model view, and Unknown/stale evidence is explained according to the configured model, without a deep model-authoring detour.

**If this fails:** If the command fails, check HealthModelResourceId in demo.local.json. If the view shows Unknown, explain it as missing or stale evidence under the model's rules, not as healthy. If the view will not load, show the rehearsal capture.

**Speaker explanation:** Say: three green lights answer three different questions: the server exists, the server is reporting, the order completed. Only the last one is what the customer feels. Ask: who acts next, and what would a new successful order prove? Transition: section 2, Secure: who is allowed to take that action, and how is it protected?

**Attendee takeaway:** Health views combine evidence under a chosen design. A green resource inventory row, a fresh heartbeat and a completed customer order answer different questions.

## If the live demo fails

If a query or the portal is slow, show the rehearsal capture of the same query with its target, store, time window and collection timestamp, and name the step you would have run.

## Timing and handoff

Ingestion and the query or view refresh are separate delays. The order result returned to the client is immediate, but its stage rows reach Log Analytics a few minutes later; say so and avoid repeated polling on stage.
