# H23F — Update Manager across every estate: assess, schedule, patch, prove

Slide 47 · Rehearsal target: 3 minutes

What this demo shows and why: most teams patch each estate with its own tool, so nobody can answer 'is everything patched?' in one place. Azure Update Manager works on Azure VMs and Arc-enabled servers alike, so one view, one schedule and one run can cover on-premises and AWS servers. We show it in four steps: one view of pending updates, how a schedule picks machines by tag, one run that patches an on-premises and an AWS test machine together, and proof that it worked.

## Before delivery

- Names used in this runbook: ring0-canary is the value of the UpdateRing tag on the first, low-risk machines patched in each cycle (the canaries); the ring0 maintenance configuration is the schedule for them. cas26-arcwin01 is the on-premises canary and iic-cas26-dev-web-01 an AWS dev canary. The IIC workers (including the on-premises worker cas26-lnx01) carry the sample application's orders and are never patched live.
- To reproduce: Arc-enabled servers (and, optionally, Azure VMs) with periodic assessment on (the built-in Azure Policy that configures periodic checking for missing system updates does this), a maintenance configuration with a dynamic scope filtered on your own tags, an agreed reboot setting, and Azure CLI with the resource-graph and connectedmachine extensions.
- Presenter lab: copy config/demo.example.json to config/demo.local.json and fill in the real identifiers (from the CAS26 Key Vault); sign in with az login and select the workload subscription before loading context. Use PowerShell 7 from the repository root. Local validation is not proof that the cloud steps will work.
- Presenter lab: Update Manager is deployed per the lab update-management design: periodic-assessment policy at the operations and AWS resource groups, five ring maintenance configurations (dev ring0/ring1, prd ring1/ring2, prd SQL) with dynamic scopes, and the UpdateRing/Environment/Workload tags on every CAS26 Arc machine.
- Presenter lab: patch canaries only, never the IIC workers or production machines. Confirm both canaries still carry UpdateRing=ring0-canary and appear in the ring0 dynamic scope; if a rehearsal moved one to another ring, put it back before delivery.
- Presenter lab: the Azure part of the one view needs an Azure VM with periodic assessment in scope; the lab scopes Update Manager to the Arc machines in the two CAS26 resource groups. Check in rehearsal which Azure VMs appear in Update Manager > Machines and in the step 1 query; if none, say that the same list and query include Azure VMs natively rather than implying one is on screen.
- Presenter lab: ServiceUrl in demo.local.json is the IIC order endpoint used by the fresh order in step 5. Set $AwsCanary to the AWS canary's Arc machine name in the presenter terminal before the demo (for example $AwsCanary = 'iic-cas26-dev-web-01').
- Rehearse the one-time update so its duration is known; choose security classification only and a reboot setting agreed with the machine owners.

## 1. One view: pending updates for Azure, on-premises and AWS machines

Mode: read-only

Open Azure Update Manager > Machines for the CAS26 subscription and show Azure, on-premises and AWS machines in one list with their pending updates. Then load context and run the prepared Resource Graph query: pending critical and security updates per machine (Arc machines and Azure VMs) in the operations and AWS resource groups, with an estate column and each assessment time. One list, one query; where a machine runs is only a column.

```powershell
. ./sessions/hybrid-operations-2026/demos/scripts/Enter-DemoContext.ps1 -ConfigPath ./sessions/hybrid-operations-2026/demos/config/demo.local.json
$q = @"
patchassessmentresources
| where type in~ ('microsoft.hybridcompute/machines/patchassessmentresults', 'microsoft.compute/virtualmachines/patchassessmentresults')
| extend rg = tostring(split(id, '/')[4]), machine = tostring(split(id, '/')[8])
| where rg in~ ('$($Demo.OperationsResourceGroup)', '$($Demo.AwsResourceGroup)')
| extend estate = case(type has 'microsoft.compute', 'Azure', rg =~ '$($Demo.AwsResourceGroup)', 'AWS', 'On-premises')
| project estate, machine, rg, os = tostring(properties.osType),
    critical = toint(properties.availablePatchCountByClassification.critical),
    security = toint(properties.availablePatchCountByClassification.security),
    assessedAt = todatetime(properties.lastModifiedDateTime)
| order by estate asc, machine asc
"@
az graph query -q $q --first 50 -o table
```

**Expected evidence:** One list and one query result show machines from every estate together, each with pending counts and a recent assessment time.

**If this fails:** If a machine is missing, check that it is Arc-connected and in scope of the periodic-assessment policy; say so rather than substituting another machine.

**Speaker explanation:** Step one, one view. Nobody should have to open three tools to answer "is everything patched?": here is every estate in one list and one query, and where a machine runs is just a column.

**Attendee takeaway:** One Update Manager view and one Resource Graph query answer "what is pending?" for Azure, on-premises and AWS machines together.

## 2. How machines get picked: the ring0 schedule and its dynamic scope

Mode: portal

In Azure Update Manager, open Maintenance configurations and the ring0 dev configuration. Read the window, the classifications and the reboot setting. Then open Dynamic scopes and read the tag filter (Environment and UpdateRing) and the machines it matched from both estates: the on-premises demo machines and the AWS dev machines, none listed by hand.

**Expected evidence:** One schedule selects machines from on-premises and AWS by tag, not by a hand-maintained list.

**If this fails:** If the scope shows no machines, the tags or the scope filter are wrong; show the filter and the machine tags side by side.

**Speaker explanation:** Step two, how machines get picked. The maintenance configuration is the window; the dynamic scope picks machines by tag. A newly onboarded server with the right tags joins this window on its own; nobody edits a machine list.

**Attendee takeaway:** A maintenance configuration sets the window; a tag-based dynamic scope decides which machines, from any estate, it patches.

## 3. Run it: patch one on-premises and one AWS canary in the same window

Mode: change

In Update Manager > Machines, select the on-premises canary (cas26-arcwin01) and the AWS dev canary, choose One-time update, tick Security only, set the rehearsed maximum duration and reboot setting, and start it. Explain while it runs; do not wait on screen for a reboot.

**Expected evidence:** A single one-time update is running on one on-premises and one AWS machine.

**If this fails:** If a machine is not eligible (disconnected, unsupported OS or already patched), state the reason from the portal and continue with the other.

**Speaker explanation:** Step three, run it. One run, two estates: an on-premises canary and an AWS canary, patched in the same window. Canaries only: the IIC workers are patched later in their own ring, one estate per window.

**Attendee takeaway:** One update run patches machines in different estates in the same window, starting with canaries.

## 4. Prove it: update history and a fresh assessment for each machine

Mode: read-only

Open Update Manager > History, select the one-time run and read the result, duration and installed updates for each machine. Then run the commands to trigger a fresh assessment on both machines (the first line stops if $AwsCanary is not set) and rerun the step 1 query.

```powershell
if (-not (Get-Variable AwsCanary -ErrorAction SilentlyContinue)) { throw 'Set $AwsCanary to the AWS canary Arc machine name first.' }
az connectedmachine assess-patches --resource-group $Demo.OperationsResourceGroup --name ($Demo.OnPremArcResourceId.Split('/')[-1])
az connectedmachine assess-patches --resource-group $Demo.AwsResourceGroup --name $AwsCanary
```

**Expected evidence:** Each machine has a run result and a newer assessment time; pending security counts are lower, or the remaining ones are explained.

**If this fails:** If the assessment has not refreshed yet, show the previous result with its time and say the refresh is still running.

**Speaker explanation:** Step four, prove it. The history proves the run happened; the fresh assessment shows what is still pending on each machine afterwards.

**Attendee takeaway:** A completed run and a fresh assessment are different evidence; read both, with their times, for each machine.

## 5. Prove it: place a fresh IIC order, then debrief

Mode: read-only

Place one demo-tagged IIC order with the shared order client and read its CorrelationId, status and per-stage results: the service still works across Azure, on-premises and AWS. The canaries are not in the order path, so this order shows the service kept working through the window; after the ring2 window that patches the IIC workers, the same order is the recovery proof. Debrief in one sentence, then transition.

```powershell
if ($Demo.ServiceUrl -match '^PENDING|REPLACE_WITH') { throw 'Populate ServiceUrl in demo.local.json with the IIC order endpoint before delivery.' }
$order = & ./sessions/hybrid-operations-2026/demos/scripts/Invoke-Cas26Request.ps1 -BaseUri $Demo.ServiceUrl -DemoTag
$order | Select-Object CorrelationId, OrderNumber, Origin, Status, ElapsedMs
$order.Stages | Format-Table Cloud, Component, Stage, Success, DurationMs
```

**Expected evidence:** A fresh order completes with every stage answered; the audience can name the schedule, the tag rule, the run result, the fresh assessment and the working service.

**If this fails:** If the order fails or times out, show its stage results and name the stage that failed; do not claim the service is fine. The guard stops the step if ServiceUrl is still a placeholder.

**Speaker explanation:** Debrief: a patch run proves the run; fresh compliance and a working service prove the outcome. Transition: keeping the Kubernetes cluster the way Git says.

**Attendee takeaway:** A patch run proves the run; fresh compliance and a working service prove the outcome.

## Reset and verification

Nothing to reset: this demo changes no tags or schedules. Installed updates stay installed; do not uninstall patches as a reset. Leave the maintenance configurations, dynamic scopes, tags and policy assignments in place, and confirm both canaries are back online after any reboot.

## If the live demo fails

If a run or assessment is slow, show the rehearsal capture of the one-view query, the ring0 dynamic-scope membership, the one-time run history and fresh assessment for both canary machines, and a fresh order, and name the step you would have run. Never present an unrun patch job as completed.

## Timing and handoff

A one-time update and any reboot take minutes: start it in step 3, explain while it runs, and read the history in step 4. An assessment refreshes a few minutes after a manual trigger; if it has not, use the previous result with its time. The fresh order in step 5 returns immediately.
