# M03 — Follow the controlled fault, then prove recovery with a fresh order

Slide 23 · Rehearsal target: 5 minutes

Slides 23 (stage 1: the marvin fault) and 34 (stage 2: recovery). Stage 1 sets the AWS worker to Fail (fault marvin) for demo-tagged orders only, places fresh orders and follows them: the AWS fulfillment stage fails, the orders fail, and the machines stay healthy. In IIC the AWS worker is inside the order path, so its fault is the cause and the evidence proves it. Stage 2 resets the worker to Healthy, places new orders with new correlation IDs and watches the model and alert catch up: recovery is a new observation, not a recycled screenshot.

## Before delivery

- PowerShell 7 from the repository root on the presenter jump, Azure CLI signed in to the CAS26 tenant with the log-analytics and resource-graph extensions installed during preparation, never on stage.
- Copy config/demo.example.json to config/demo.local.json (gitignored) and fill every identifier with a verified value. Run the context loader with -Offline first, then without it.
- Read access only is needed for every read-only step: Log Analytics Reader on the workspace, Reader on the monitoring RG and the AWS connector RG. No step changes an Azure or AWS resource except the application-level worker mode in M03.
- Before delivery confirm: the AWS worker on iic-cas26-prd-api-01 (AwsWorkerInstanceId) is in Healthy mode and reads /var/lib/cas26/worker-state.json on every message; the AWS CLI on the jump is signed in with ssm:SendCommand and ssm:GetCommandInvocation on that instance only; the M02 baseline orders are in $baselineOrders and $baseline.
- Only the AWS worker's application mode changes. Never stop the service, the instance, EKS, the ALB, the Arc agent or any network path. MaxMinutes 15 is the automatic backstop; the reset in stage 2 is the planned end.
- Decide the presenter's stop condition before starting: if the fault command reports anything other than PreviousMode Healthy and Mode Fail, stop and reset.

## 1. Stage 1 (slide 23): preview the fault on the AWS worker

Mode: preparation

Load the context and run the fault command as a dry run. It reads the worker's current state over SSM and prints the file it would write, without writing it. Confirm the target is the AWS worker and its current mode is Healthy.

```powershell
$S = './sessions/azure-monitor-hybrid-multicloud-observability/demos'
. $S/scripts/Enter-DemoContext.ps1 -ConfigPath $S/config/demo.local.json
pwsh ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Set-Cas26WorkerMode.ps1 -Mode Fail -InstanceId $Demo.AwsWorkerInstanceId -AwsRegion $Demo.AwsRegion -MaxMinutes 15 -DryRun
if ($LASTEXITCODE -ne 0) { throw 'Fault preview failed; no change is authorized.' }
```

**Expected evidence:** DRY RUN line naming the instance and /var/lib/cas26/worker-state.json, current mode Healthy, proposed mode Fail with faultName marvin and expires_at 15 minutes ahead.

**If this fails:** Preview fails: SSM or AWS identity problem; do not attempt the change; fix the AWS sign-in and preview again, or show the rehearsal capture. The file is reported as not owned by CAS26: stop; something else owns that path.

**Speaker explanation:** A fault is only safe if it is previewed, bounded and reversible. The dry run shows all three before anything changes.

**Attendee takeaway:** Preview every fault command and confirm its target and expiry before applying it.

## 2. Stage 1 (slide 23): set the AWS worker to Fail (marvin) for demo-tagged orders

Mode: change

Apply the fault. The worker now returns a deliberate failed stage result for demo-tagged orders only; untagged orders are unaffected, and the service, instance and network are untouched.

```powershell
pwsh ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Set-Cas26WorkerMode.ps1 -Mode Fail -InstanceId $Demo.AwsWorkerInstanceId -AwsRegion $Demo.AwsRegion -MaxMinutes 15
if ($LASTEXITCODE -ne 0) { throw 'Fault change failed; reset with -Mode Healthy before continuing.' }
```

**Expected evidence:** Output with Mode Fail, FaultName marvin, PreviousMode Healthy, Changed True and an ExpiresAt time.

**If this fails:** Any error: run the reset command immediately and show the rehearsal capture. Do not retry the fault more than once on stage.

**Speaker explanation:** This is the only change in the session: one file on one worker, application-level, with an expiry. Everything else we do is observation.

**Attendee takeaway:** Fault the application behaviour you own, not the infrastructure other people depend on.

## 3. Stage 1 (slide 23): place fresh demo-tagged orders

Mode: change

Place three new orders with the demo tag, two seconds apart: the service-failure alert only judges a window with at least three orders. The client result already tells the story: each order failed and the failure mode is marvin. Keep the correlation IDs.

```powershell
$failed = @(& ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Invoke-Cas26Request.ps1 -BaseUri $Demo.ServiceUrl -DemoTag -Count 3 -IntervalSeconds 2 -JsonLinesPath $S/evidence/local/m03-marvin.jsonl)
$failed | Select-Object CorrelationId, OrderNumber, Origin, Status, ElapsedMs, FailureMode
$failed[0].Stages | Format-Table Cloud, Component, Stage, Success, DurationMs
```

**Expected evidence:** Three results with Status Failed, FailureMode marvin and new CorrelationIds; in each, the AwsWorker stage has Success False while the OnPremWorker stage succeeded.

**If this fails:** Status Completed: the orders were not demo-tagged or the worker did not read the new state; check the file with a DryRun. The portal itself still loads: that is part of the point.

**Speaker explanation:** The portal answered, Front Door routed, the coordinator accepted: the customer still did not get an order. Front-end availability is not order completion.

**Attendee takeaway:** A working portal and a completed order are different commitments.

## 4. Stage 1 (slide 23): read the failed order's stages

Mode: read-only

Query the stage records for the first failed order and read them as a timeline. Then run the service outcome to see how the service counts the orders.

```powershell
$q = (Get-Content "$S/src/queries/order-journey.kql" -Raw).Replace('<CORRELATION_ID>', $failed[0].CorrelationId)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
$q = Get-Content "$S/src/queries/service-outcome.kql" -Raw
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** AwsWorker Failed with Success false and FailureMode marvin; OnPremWorker Completed; Coordinator Failed. In the outcome list the three marvin orders are Failed with FailedComponents [AwsWorker, Coordinator], next to the Completed baseline orders.

**If this fails:** No AwsWorker row at all: the worker did not report, which is a different fault (missing evidence, later Unknown); say so rather than calling it marvin. If ingestion is slow, show src/fixtures/order-marvin.jsonl as the rehearsal capture and name the step.

**Speaker explanation:** The evidence points at one stage in one cloud, with the fault name on the row. Investigation starts from the customer outcome and walks back to the first failed stage.

**Attendee takeaway:** Walk back from the failed outcome to the first failed stage; the fault name on the row confirms a controlled fault.

## 5. Stage 1 (slide 23): see the order fail while the machines stay healthy

Mode: read-only

Check the AWS worker machine's Heartbeat and CPU for the same window, then glance at the Health Model. The machine is fine; the order is not. Infrastructure health cannot stand in for the customer outcome.

```powershell
$q = "Heartbeat | where TimeGenerated > ago(15m) | where _ResourceId =~ '$($Demo.AwsWorkerArcResourceId)' | summarize LastSeen=max(TimeGenerated), Beats=count() by Computer"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
$q = "Perf | where TimeGenerated > ago(15m) | where _ResourceId =~ '$($Demo.AwsWorkerArcResourceId)' | where CounterName == '% Processor Time' and InstanceName == '_Total' | summarize AvgCpu=avg(CounterValue), LastSeen=max(TimeGenerated)"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
# Portal: Monitor > Health models > hm-tplabs-cas26-service-cus-01 > graph
```

**Expected evidence:** Heartbeat for iic-cas26-prd-api-01 fresh (about one beat a minute) and total CPU unremarkable during the fault. In the model graph, after its window, the Arc-enabled AWS worker is Unhealthy on its stage evidence, AWS fulfillment and pricing is Unhealthy, Customers can complete an order is Unhealthy and the service root follows; the portal commitment stays Healthy.

**If this fails:** Heartbeat missing: that is a real monitoring problem on the machine, not part of this fault; name it. If the query is slow, src/fixtures/heartbeat-aws-worker.jsonl is the rehearsal capture of the machine staying fresh through the fault window. The model has not changed yet: its window is five minutes; come back to it in M04.

**Speaker explanation:** This is the SCOM lesson in one screen: every host green, the service red. Health has to be defined by the customer commitment, with the machines as evidence.

**Attendee takeaway:** Machine health is supporting evidence; the customer outcome is the signal.

## 6. Stage 2 (slide 34): set the AWS worker back to Healthy

Mode: change

After the response teaching, reset the worker. The command reads the current state first, so the output shows it moved from Fail back to Healthy.

```powershell
$S = './sessions/azure-monitor-hybrid-multicloud-observability/demos'
. $S/scripts/Enter-DemoContext.ps1 -ConfigPath $S/config/demo.local.json
pwsh ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Set-Cas26WorkerMode.ps1 -Mode Healthy -InstanceId $Demo.AwsWorkerInstanceId -AwsRegion $Demo.AwsRegion
if ($LASTEXITCODE -ne 0) { throw 'RECOVERY FAILED: restore the AWS worker before proceeding.' }
```

**Expected evidence:** Mode Healthy, PreviousMode Fail, Changed True (the worker, not the script, applies the expiry).

**If this fails:** Failure: retry once; if it still fails, the worker stops applying the fault at expires_at by itself; say so and show the recovery capture. Never leave the session with the worker in Fail.

**Speaker explanation:** The management command succeeding tells us the file changed. It does not tell us a customer can order again; only a new order can.

**Attendee takeaway:** A successful reset command is not recovery evidence.

## 7. Stage 2 (slide 34): place new demo-tagged orders

Mode: change

Place three fresh orders, two seconds apart. Each must have a new correlation ID; reusing the baseline would prove nothing about now. Three orders also give the model and the alert a full window of good samples.

```powershell
$recovered = @(& ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Invoke-Cas26Request.ps1 -BaseUri $Demo.ServiceUrl -DemoTag -Count 3 -IntervalSeconds 2 -JsonLinesPath $S/evidence/local/m03-recovery.jsonl)
$recovered | Select-Object CorrelationId, OrderNumber, Origin, Status, ElapsedMs, FailureMode
$used = @($baselineOrders.CorrelationId) + @($failed.CorrelationId)
if (@($recovered.CorrelationId | Where-Object { $_ -in $used }).Count) { throw 'Not a new order.' }
```

**Expected evidence:** Three results with Status Completed, empty FailureMode, and CorrelationIds different from every baseline and failed order.

**If this fails:** Still Failed with marvin: the worker has not re-read the state; check with a DryRun and wait one message. Failed with another mode: another fault is active; stop and investigate before claiming recovery.

**Speaker explanation:** Recovery is a new observation of the same commitment: a new order, placed now, that completes.

**Attendee takeaway:** Prove recovery with a new transaction, not with the last good screenshot.

## 8. Stage 2 (slide 34): confirm every stage and the order completed

Mode: read-only

Read the first recovery order's stages and the service outcome. The list now shows the baseline orders Completed, the marvin orders Failed and the recovery orders Completed, in that order of time.

```powershell
$q = (Get-Content "$S/src/queries/order-journey.kql" -Raw).Replace('<CORRELATION_ID>', $recovered[0].CorrelationId)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
$q = (Get-Content "$S/src/queries/service-outcome.kql" -Raw).Replace('ago(window)', 'ago(2h)')
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** Seven successful stage rows for the recovery order ending in Coordinator Completed; the outcome list shows Completed, Failed, Completed across the three groups of orders.

**If this fails:** Rows missing: ingestion delay; wait once. If the rows are slow to arrive, show src/fixtures/order-recovery.jsonl as the rehearsal capture and name the step.

**Speaker explanation:** Three groups of orders, each with its own correlation IDs, one story: normal, controlled failure, recovered. The evidence carries the timeline.

**Attendee takeaway:** Keep the failed and the recovered order side by side; the comparison is the proof.

## 9. Stage 2 (slide 34): watch the model and the alert catch up

Mode: read-only

Open the Health Model graph and the alert list. The model returns to Healthy once its five-minute window holds enough good samples; the alert resolves on its own evaluation schedule. Record both times against the order times.

```powershell
$arg = "alertsmanagementresources | where type =~ 'microsoft.alertsmanagement/alerts' | where todatetime(properties.essentials.startDateTime) > ago(2h) | project name=tostring(properties.essentials.alertRule), condition=tostring(properties.essentials.monitorCondition), state=tostring(properties.essentials.alertState), started=todatetime(properties.essentials.startDateTime), changed=todatetime(properties.essentials.lastModifiedDateTime)"
az graph query --subscriptions $Demo.MonitoringSubscriptionId -q $arg -o table
# Portal: Monitor > Health models > hm-tplabs-cas26-service-cus-01 > graph and history
```

**Expected evidence:** The service-failure alert (CAS26 service: request failures) fired on the first 5-minute evaluation after the three marvin orders (at least three orders, half or more failed) and shows Resolved about 15 minutes after the last failing window, because a stateful log search alert resolves only after three consecutive evaluations without the condition. The model's AWS worker, AWS fulfillment and Customers can complete an order entities return to Healthy once the window holds the three recovery orders and no failures. Each state change has a time later than the order that caused it.

**If this fails:** The alert still shows Fired: it resolves after three clean 5-minute evaluations; read its last-modified time instead of refreshing. The model reads Unknown: no orders in its five-minute window, which is the correct reading of silence; place one more demo-tagged order if time allows.

**Speaker explanation:** Four clocks: the order, ingestion, model evaluation and alert evaluation. Recovery is complete when the customer order succeeds; the model and alert confirm it later, and we can say how much later.

**Attendee takeaway:** Know how long your model and alerts lag behind the customer outcome.

## Timing and handoff

The failed orders return in seconds; their rows need ingestion time; the Health Model re-evaluates on its refresh interval (PT1M) over its window (PT5M); the service-failure alert evaluates every 5 minutes over a 5-minute window, fires on the first evaluation that sees at least three orders with half or more failed, and, being stateful, resolves after three consecutive evaluations without the condition, about 15 minutes after the last failing window. Stage 2 happens later in the deck, which is the time the model and alert need.
