# M02 — Place a baseline order and read the service view

Slide 20 · Rehearsal target: 4 minutes

Slides 20 (stage 1 of 2) and 21 (stage 2 of 2). Stage 1 places demo-tagged IIC orders through Front Door (the first is the baseline order we follow) and reads the baseline's stage records by correlation ID, so failure and recovery have a comparison point. Stage 2 reads the service view in the fixed order taught on slide 19 (customer outcome, overall health, components and dependencies, evidence freshness, drill-down with owners) and checks that the view agrees with the raw stage records and that both portal origins are healthy.

- Copy config/demo.example.json to config/demo.local.json (gitignored) and fill every identifier with a verified value. Run the context loader with -Offline first, then without it.

- Before delivery confirm: both portal origins healthy in Front Door, both workers in Healthy mode, and ServiceUrl, FrontDoorProfileResourceId and WorkbookResourceId recorded in demo.local.json.
- Open the workbook "CAS26 service operations" in a browser tab before the session, set to the last 30 minutes, light theme.

## 1. Stage 1 (slide 20): check the starting state

Mode: preparation

Load the context and confirm the starting state: the AWS worker must be in Healthy mode before the baseline. The dry run reads the worker's mode over SSM without changing it.

```powershell
$S = './sessions/azure-monitor-hybrid-multicloud-observability/demos'
. $S/scripts/Enter-DemoContext.ps1 -ConfigPath $S/config/demo.local.json
pwsh ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Set-Cas26WorkerMode.ps1 -Mode Healthy -InstanceId $Demo.AwsWorkerInstanceId -AwsRegion $Demo.AwsRegion -DryRun
if ($LASTEXITCODE -ne 0) { throw 'Worker state could not be read; check the AWS CLI sign-in on the jump.' }
```

**Expected evidence:** A DRY RUN line showing the AWS worker is already Healthy; no change is needed.

**If this fails:** DryRun fails: the AWS CLI or SSM path from the jump is not signed in; fix it before continuing. PreviousMode other than Healthy: a fault was left on; reset it with -Mode Healthy before the baseline.

**Speaker explanation:** A baseline only means something if we know the starting state. The dry run reads the worker's mode without changing it.

**Attendee takeaway:** Record the starting state before taking a baseline.

## 2. Stage 1 (slide 20): place demo-tagged orders through Front Door

Mode: change

Place three orders with the demo tag through the public Front Door endpoint, two seconds apart, so the five-minute window holds the three samples the health signals need. The first is the baseline order we follow: record its correlation ID, order number, serving origin (Azure or AWS), status and elapsed time. The correlation ID is the key for everything that follows; the order number is for people.

```powershell
$baselineOrders = @(& ./sessions/azure-monitor-hybrid-multicloud-observability/demos/scripts/Invoke-Cas26Request.ps1 -BaseUri $Demo.ServiceUrl -DemoTag -Count 3 -IntervalSeconds 2 -JsonLinesPath $S/evidence/local/m02-baseline.jsonl)
$baseline = $baselineOrders[0]
$baselineOrders | Select-Object CorrelationId, OrderNumber, Origin, Status, ElapsedMs, FailureMode
$baseline.Stages | Format-Table Cloud, Component, Stage, Success, DurationMs
```

**Expected evidence:** Three results with Status Completed and new CorrelationIds, served by the Azure or AWS origin; the baseline order's stages from Azure, OnPrem and AWS are all successful.

**If this fails:** Status Failed with a FailureMode: a fault mode is still active; reset and re-place. TimedOut: note the time and find the order by time window in step 3. A contract error from the script means the endpoint's response shape changed; stop and show the rehearsal capture.

**Speaker explanation:** These are application writes, three demo-tagged orders, nothing else. The client sees the answer first; the evidence follows through ingestion.

**Attendee takeaway:** One correlation ID is the thread that ties a customer order to every stage in every cloud.

## 3. Stage 1 (slide 20): read the order's stage records

Mode: read-only

Query the workspace for this correlation ID. The rows are the evidence of what happened, independent of what the client was told.

```powershell
$q = (Get-Content "$S/src/queries/order-journey.kql" -Raw).Replace('<CORRELATION_ID>', $baseline.CorrelationId)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** Seven rows in time order: Coordinator Accepted (with Origin), Transport Dispatched, OnPremWorker and AwsWorker Started and Completed, then Coordinator Completed with Success true.

**If this fails:** No rows yet: ingestion delay; wait once, then re-run. Fewer rows: a stage did not report; that is the finding. If ingestion is slow on stage, show src/fixtures/order-baseline.jsonl as the rehearsal capture.

**Speaker explanation:** Read the rows as a timeline across three clouds. The last row, Coordinator Completed, is the customer outcome; the others explain it.

**Attendee takeaway:** Query stage records by the correlation ID, never by the display order number.

## 4. Stage 1 (slide 20): judge the order as the service sees it

Mode: read-only

Run the service-outcome query. It summarizes by correlation ID first, so each order counts once, and marks it Completed only when the coordinator wrote its Completed row. Confirm the baseline is Completed inside the target.

```powershell
$q = Get-Content "$S/src/queries/service-outcome.kql" -Raw
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** The three baseline orders, each listed once with Outcome Completed, Clouds [Azure, OnPrem, AWS] and ElapsedMs inside the order target.

**If this fails:** The order appears as Unresolved: the coordinator's Completed row has not arrived yet or was never written. Several rows for one order means the query was edited to skip the summarize-by-CorrelationId step.

**Speaker explanation:** Counting rows would count stages, not customers. Summarizing by correlation ID first turns seven stage rows into one customer outcome.

**Attendee takeaway:** Summarize by correlation ID before you count successes.

## 5. Stage 2 (slide 21): open the service view and read it in the fixed order

Mode: portal

Open the workbook and read it in the order slide 19 taught: 1 the customer outcome (order success, latency, last good order), 2 overall health (state, freshness, affected commitment), 3 components and dependencies (portal origins, coordinator, both workers), 4 evidence freshness (latest timestamps, late sources), 5 drill-down (correlation ID, stage timeline and owners). Say what each panel answers before looking at its colour.

```powershell
az resource show --ids $Demo.WorkbookResourceId --query "{name:properties.displayName, updated:properties.timeModified, source:properties.sourceId}" -o table
# Portal: Azure portal > Monitor > Workbooks > CAS26 service operations (RG rg-tplabs-cas26-mon-eus-01), time range last 30 minutes
```

**Expected evidence:** The workbook is the one named and recently modified, and its panels follow that order: the baseline orders in the customer-outcome panel, overall health Healthy, both origins, the coordinator and both workers green, every source fresh, and the drill-down ready for a correlation ID.

**If this fails:** The workbook does not open: check Reader on the monitoring RG. A panel reports a query error: name the panel and read the same answer from the raw query in step 4.

**Speaker explanation:** A service view is read in a fixed order so that a green component never distracts from a failed customer outcome. The workbook drills down; the Health Model, later, evaluates.

**Attendee takeaway:** Read a service view from customer outcome to overall health to components to freshness to drill-down.

## 6. Stage 2 (slide 21): open the baseline order's stages in the view

Mode: portal

In the correlation panel, select the baseline order's correlation ID and compare what the view shows with the raw rows from step 3. The view is only trustworthy if it agrees with the rows.

```powershell
$baseline.CorrelationId | Set-Clipboard
# Portal: paste into the workbook's correlation panel filter and compare stage by stage with the query result from step 3
```

**Expected evidence:** The view shows the same seven stages, the same clouds and the same success values as the raw query. Any difference is a view defect to record.

**If this fails:** The panel shows a different stage count: its time range or filter differs from the query; align them before calling it a view defect, and record any difference that remains.

**Speaker explanation:** The view is a lens on the evidence, not the evidence. We prove it by matching one order's rows exactly.

**Attendee takeaway:** Check one known order in the view against the raw records before trusting the view.

## 7. Stage 2 (slide 21): check both portal origins

Mode: read-only

The portal is redundant: Front Door serves it from Azure Container Apps and from the AWS ALB/EKS origin. Read the origin health metric and which origins served recent orders. One healthy origin keeps customers in; two is the design target.

```powershell
az monitor metrics list --resource $Demo.FrontDoorProfileResourceId --metric OriginHealthPercentage --interval PT5M --offset 1h --aggregation Average -o table
$q = "Cas26Service_CL | where TimeGenerated > ago(30m) | where Component == 'Coordinator' and Stage == 'Accepted' | summarize Orders=dcount(CorrelationId), Last=max(TimeGenerated) by Origin"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** Origin health near 100 percent, and recent orders served by both Azure and AWS origins. One origin at 0 would make the portal Degraded, not down.

**If this fails:** The metric is empty: check FrontDoorProfileResourceId and the time range. Only one origin appears in the orders: routing weights or a small sample; place a few more orders with -Count 3 if time allows.

**Speaker explanation:** Portal availability and order completion are different commitments. Two origins behind Front Door protect the first; the second depends on both workers.

**Attendee takeaway:** Treat redundant origins as one commitment with a degraded state, not as two separate alarms.

## 8. Stage 2 (slide 21): note freshness and owners

Mode: read-only

Finish the reading with freshness and ownership: when did each source and each stage last report, and who owns each component? The owner is what turns a red tile into an action.

```powershell
$q = (Get-Content "$S/src/queries/evidence-freshness.kql" -Raw).Replace('<AWS_RESOURCE_GROUP>', $Demo.AwsResourceGroup)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
# Owners (from the lab design): Coordinator and Transport - Azure application team; OnPremWorker - private cloud team; AwsWorker - AWS workload team; telemetry routes - monitoring team
```

**Expected evidence:** Every stage and every source Fresh, and a named owner for each component the view shows.

**If this fails:** Stale stage rows while the order was just placed: ingestion delay; re-read the timestamp, do not re-run in a loop. A component with no owner is a gap to record in the evidence notes.

**Speaker explanation:** Freshness tells us whether we may believe the colours; owners tell us who acts. Both belong in the view, not in someone's head.

**Attendee takeaway:** Every panel in a service view needs a freshness time and an owner.
