# M04 — Inspect the model configuration, then explain the current state from evidence

Slide 29 · Rehearsal target: 6 minutes

Slides 29 (stage 1 of 2) and 30 (stage 2 of 2). Stage 1 opens the IIC health model and reads its configuration in the order stage 2 uses: entities, relationship direction, one signal's query, window and thresholds, aggregation and missing-data behaviour. Stage 2 explains state from evidence: current stage records and timestamps, the signal's value against its rule, aggregation to the commitment and propagation to the service, from Healthy at baseline to AWS fulfillment Unhealthy during the marvin fault. If evidence is stale, the honest state is Unknown.

## 1. Stage 1 (slide 29): open the IIC health model

Mode: read-only

Open the model in the portal and read its resource properties from ARM. Note the region (Central US, because East US is not a supported preview region), the identity it uses to read evidence, and the provisioning state.

```powershell
$S = './sessions/azure-monitor-hybrid-multicloud-observability/demos'
. $S/scripts/Enter-DemoContext.ps1 -ConfigPath $S/config/demo.local.json
$hm = "https://management.azure.com$($Demo.HealthModelResourceId)"; $api = "api-version=$($Demo.HealthModelApiVersion)"
az rest --method get --url "$($hm)?$api" --query "{name:name, location:location, state:properties.provisioningState, identity:identity.type}" -o table
# Portal: Azure portal > Monitor > Health models > hm-tplabs-cas26-service-cus-01
```

**Expected evidence:** hm-tplabs-cas26-service-cus-01 in centralus, Succeeded, with a user-assigned identity. The portal graph opens.

**If this fails:** An API-version error: use the version in the prerequisites and note it. Not found: wrong subscription in HealthModelResourceId.

**Speaker explanation:** The model is an Azure resource with its own identity; that identity, not the presenter, reads the evidence. That matters when a signal goes Unknown for lack of permission.

**Attendee takeaway:** A health model reads evidence with its own identity; check it has access to every source.

## 2. Stage 1 (slide 29): read the entities

Mode: read-only

List the model's entities with their display names, impact and current health, and keep them for the next steps. Compare them with the IIC tree: the service, its three commitments, and the branches and components beneath each.

```powershell
$entities = (az rest --method get --url "$hm/entities?$api" -o json | ConvertFrom-Json).value
$entities | Select-Object name, @{n='displayName';e={$_.properties.displayName}}, @{n='impact';e={$_.properties.impact}}, @{n='health';e={$_.properties.healthState}} | Format-Table -AutoSize
```

**Expected evidence:** The root entity IIC Hybrid Orders; the three commitments Customers can open the portal, Customers can complete an order and Operators can observe the service; beneath them Global entry and protection, Cloud portal origins (Azure Container Apps origin, AWS ALB -> EKS origin), Azure request coordination (Function coordinator, Service Bus transport), On-premises order validation (the cas26-lnx01 workload VM and its SDN egress path), AWS fulfillment and pricing (the Arc-enabled AWS worker iic-cas26-prd-api-01), and Log Analytics ingestion and Azure Monitor workspace metrics.

**If this fails:** No healthState column: the property name differs in this API version; read the state in the portal instead. Entities that differ from the tree: someone changed the model; read, do not fix.

**Speaker explanation:** Entities are commitments and components, named in plain words. The tree on screen is the tree we drew: service, three commitments, then the parts each commitment needs.

**Attendee takeaway:** Name entities after commitments customers recognise, then add the components beneath them.

## 3. Stage 1 (slide 29): read relationship direction

Mode: read-only

List the relationships. Each one says a parent depends on a child, so the child's health propagates upward. Direction is what makes a worker fault reach the customer commitment.

```powershell
$display = @{}; $entities | ForEach-Object { $display[$_.name] = $_.properties.displayName }
$relationships = (az rest --method get --url "$hm/relationships?$api" -o json | ConvertFrom-Json).value
$relationships | ForEach-Object { [pscustomobject]@{ Parent = $display[$_.properties.parentEntityName]; Child = $display[$_.properties.childEntityName] } } | Sort-Object Parent | Format-Table -AutoSize
```

**Expected evidence:** Parent-to-child pairs from the root to each commitment, from each commitment to its branches, and from each branch to its components, for example Customers can complete an order -> AWS fulfillment and pricing -> Arc-enabled AWS worker. Azure request coordination, On-premises order validation and AWS fulfillment and pricing are all required children of Customers can complete an order.

**If this fails:** Parent and child look reversed: read the portal graph's arrows before claiming a defect.

**Speaker explanation:** Relationships point from what you promise to what it depends on. Get the direction wrong and a failed worker never reaches the customer outcome.

**Attendee takeaway:** Draw dependency direction from the commitment down to its components.

## 4. Stage 1 (slide 29): open one signal's query, window and thresholds

Mode: read-only

Open the Customers can complete an order entity and read its Log Analytics signals: the query text, the value column, the time grain (window), the refresh interval and the Degraded and Unhealthy rules.

```powershell
$order = $entities | Where-Object { $_.properties.displayName -eq 'Customers can complete an order' }
$signals = $order.properties.signalGroups.azureLogAnalytics.signals
$signals | Format-List name, displayName, valueColumnName, timeGrain, refreshInterval, @{n='degraded';e={$_.evaluationRules.degradedRule | ConvertTo-Json -Compress}}, @{n='unhealthy';e={$_.evaluationRules.unhealthyRule | ConvertTo-Json -Compress}}
$signal = $signals | Where-Object name -eq 'request-failure-percent'
$signal.queryText
```

**Expected evidence:** request-failure-percent: FailurePercent over PT5M, refreshed PT1M, Degraded above 0, Unhealthy at or above 50, with a three-order minimum in the query. telemetry-coverage: Samples, Unhealthy below 3. The query text summarizes the stage rows by CorrelationId and counts an order Completed only on Coordinator / Completed / Success=true, the same rule as service-outcome.kql.

**If this fails:** signalGroups is empty: the signals are defined elsewhere in this API version; open the entity's Signals tab in the portal instead.

**Speaker explanation:** A colour is a rule applied to a number from a query over a window. Read all four before believing the colour, and check that the signal judges an order exactly as the service-outcome query does.

**Attendee takeaway:** For every signal, know its query, its window and its thresholds.

## 5. Stage 1 (slide 29): check aggregation and missing-data behaviour

Mode: read-only

Read how the commitment combines its children and what it does when evidence is missing: the dependency aggregation type and whether Unknown children are ignored. Then read the redundancy rule on the portal origins, and state what happens when a signal query returns no rows.

```powershell
$order.properties.signalGroups.dependencies | Format-List aggregationType, ignoreUnknown
$origins = $entities | Where-Object { $_.properties.displayName -eq 'Cloud portal origins' }
$origins.properties.signalGroups.dependencies | Format-List
# A signal whose query returns no rows (no stage records in the window, or fewer than three resolved orders) has no value: the entity shows Unknown, not Healthy.
```

**Expected evidence:** Customers can complete an order: aggregationType WorstOf and ignoreUnknown false, so the worst required child wins and an Unknown child is not ignored. Cloud portal origins: a redundancy rule, so one failed origin makes the portal Degraded and two make it Unhealthy. No valid samples means Unknown: the coverage query returns no row when the window has no stage records, and the failure query returns no row below three resolved orders.

**If this fails:** Properties absent: the portal shows them under the entity's health aggregation settings.

**Speaker explanation:** Missing evidence must never look like good news. WorstOf with Unknown not ignored is the conservative choice: silence makes the service Unknown rather than green.

**Attendee takeaway:** Configure missing data to produce Unknown, and decide explicitly how children aggregate.

## 6. Stage 2 (slide 30): start from current stage records and timestamps

Mode: read-only

Explain state from evidence, bottom up. First, what evidence exists right now for the signals to read: the last stage records per component and stage, with their age.

```powershell
$q = (Get-Content "$S/src/queries/evidence-freshness.kql" -Raw).Replace('<AWS_RESOURCE_GROUP>', $Demo.AwsResourceGroup)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** Stage rows for every component and stage (Coordinator, Transport, OnPremWorker, AwsWorker) with LastSeen times from the M02 and M03 orders, including AwsWorker / Failed from the marvin orders, and Fresh Heartbeat and Perf rows for the six AWS machines.

**If this fails:** Stage rows older than their expected age: no orders since M03, so the current window can only read Unknown; the signal history still explains the earlier states.

**Speaker explanation:** State is only as current as its newest evidence. We read timestamps before we read colours.

**Attendee takeaway:** Check evidence age before interpreting any health state.

## 7. Stage 2 (slide 30): evaluate the signal yourself

Mode: read-only

Run the signal's own query in the workspace, first for the current window and then for the five minutes of the marvin orders, and compare each value with the rules. This is exactly what the model does each refresh; doing it by hand shows there is no magic.

```powershell
$q = $signal.queryText
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
$from = ([datetime]$failed[0].PlacedAtUtc).ToUniversalTime().AddMinutes(-1).ToString('o')
$qFault = $q.Replace('TimeGenerated > ago(5m)', "TimeGenerated between (datetime($from) .. 5m)")
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $qFault -o table
```

**Expected evidence:** For the marvin window: FailurePercent at or above 50 (100 when only the three marvin orders are in it), which is Unhealthy. For the current window: a FailurePercent to compare with the rules (0 = Healthy, above 0 = Degraded, 50 or more = Unhealthy), or no row when fewer than three orders resolved in the last five minutes, which the model shows as Unknown.

**If this fails:** $failed is not in this terminal: read PlacedAtUtc from evidence/local/m03-marvin.jsonl. The query errors: record it as a signal configuration defect; the model shows an error or Unknown for that signal.

**Speaker explanation:** The model evaluates a query over a window against a rule. Running the query ourselves turns the colour into a number we can defend.

**Attendee takeaway:** Re-run a health signal's query by hand when a state surprises you.

## 8. Stage 2 (slide 30): follow aggregation to the commitment and propagation to the service

Mode: read-only

Read each entity's current state from the bottom up: worker, then the request flow, then the model root. Explain each state from the signal value and the aggregation rule, and say where the evidence stops.

```powershell
az rest --method get --url "$hm/entities?$api" --query "value[].{name:name, displayName:properties.displayName, health:properties.healthState}" -o table
# Portal: model graph; select each entity and open its signal history for the last hour
```

**Expected evidence:** In the signal history for the last hour: Healthy through the baseline window; during the marvin window the Arc-enabled AWS worker is Unhealthy on its stage evidence while its heartbeat stays fresh, AWS fulfillment and pricing is Unhealthy, Customers can complete an order is Unhealthy and IIC Hybrid Orders follows by WorstOf, while Customers can open the portal and Operators can observe the service stay Healthy. The current state matches the current window's signals, and every parent matches its worst required child.

**If this fails:** An entity shows Healthy with no samples: a signal or rule is misconfigured; record it. If states lag the evidence, point at the refresh interval and window rather than refreshing.

**Speaker explanation:** Propagation is arithmetic, not judgement: children's states combine by rule into the parent's. If we cannot explain a state from its evidence, we do not report it.

**Attendee takeaway:** Explain every state from its signal, window, rule and children, or report it as Unknown.

## 9. Stage 2 (slide 30): state the limits

Mode: read-only

Close with what the model can and cannot claim. Every branch of the IIC tree is bound, but each state is only as good as its window, its minimum samples and its freshest evidence. Name the limits, then show the baseline order's records to recall what a Healthy window is made of.

```powershell
$q = (Get-Content "$S/src/queries/order-journey.kql" -Raw).Replace('<CORRELATION_ID>', $baseline.CorrelationId)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** A spoken limits statement: a five-minute window, a three-order minimum, a one-minute refresh, and no orders in the window reads Unknown, not Healthy; machine health is supporting evidence only. The baseline order's seven successful stage rows are on screen.

**If this fails:** $baseline is not in this terminal: read the correlation ID from evidence/local/m02-baseline.jsonl. If time is short, say the limits in one sentence and move on.

**Speaker explanation:** A health model is a claim about the service. Its limits are part of the claim: the window, the minimum samples, and the places where it can only say Unknown.

**Attendee takeaway:** Publish a health model's limits together with its states.
