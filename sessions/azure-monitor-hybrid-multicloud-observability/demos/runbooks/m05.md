# M05 — Test evidence freshness and cost boundaries

Slide 38 · Rehearsal target: 2.5 minutes

Slide 38. Use the previous two slides' decision structure on real data: query the last timestamp per source and per stage, compare it with the expected cadence, run billable volume by table, then name one reduction and the diagnostic question it would lose.

## 1. Query the last timestamp per source and per stage

Mode: read-only

Run the freshness query across the three routes: Heartbeat and Perf from each Arc-connected AWS machine, and each component and stage of the order records.

```powershell
$S = './sessions/azure-monitor-hybrid-multicloud-observability/demos'
. $S/scripts/Enter-DemoContext.ps1 -ConfigPath $S/config/demo.local.json
$q = (Get-Content "$S/src/queries/evidence-freshness.kql" -Raw).Replace('<AWS_RESOURCE_GROUP>', $Demo.AwsResourceGroup)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** One row per source with LastSeen, AgeMin, ExpectedMaxAgeMin and Freshness: Heartbeat and Perf Fresh for the six AWS machines, and stage rows Fresh for each component and stage written by the recent orders.

**If this fails:** No rows: workspace or RG placeholder. No stage rows: no orders in the last 24 hours; check the order stream before continuing.

**Speaker explanation:** Freshness is the first cost question: evidence we pay for but do not receive in time answers nothing.

**Attendee takeaway:** Know the last arrival time of every evidence source you rely on.

## 2. Compare with the expected cadence

Mode: read-only

Read AgeMin against ExpectedMaxAgeMin and list what is Stale or silent. Silent sources do not appear at all, so compare with the machine list and the seven expected stages.

```powershell
$fresh = az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o json | ConvertFrom-Json
$fresh | Where-Object Freshness -ne 'Fresh' | Format-Table Source, AgeMin, ExpectedMaxAgeMin -AutoSize
$expectedStages = 'Coordinator / Accepted','Transport / Dispatched','OnPremWorker / Started','OnPremWorker / Completed','AwsWorker / Started','AwsWorker / Completed','Coordinator / Completed'
$expectedStages | Where-Object { "Stage / $_" -notin $fresh.Source }
```

**Expected evidence:** A short list of Stale sources (ideally none) and any silent expected stage. Stages written only on failure (Failed, TimedOut, DeadLettered) are not in the expected list; a silent expected stage is a finding.

**If this fails:** Everything Stale: check the time on the jump and the time range; then check ingestion. Expected ages are presenter settings in the query comments; adjust them to the real order cadence.

**Speaker explanation:** Expected cadence turns a timestamp into a verdict. And a list of what should be there is the only way to see what is missing.

**Attendee takeaway:** Write down the expected cadence for each source; without it you cannot call anything stale.

## 3. Run the billable-volume-by-table query

Mode: read-only

Run the Usage query for the last 30 full days. It shows which tables drive billable ingestion; it is workspace ingestion, not the whole bill.

```powershell
$q = Get-Content "$S/src/queries/telemetry-volume.kql" -Raw
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** Tables ordered by BillableGB. Guest telemetry (Perf, Syslog) leads; Heartbeat is small; Cas26Service_CL is tiny or absent.

**If this fails:** Empty result: the time range is too short; use a 7-day window. src/fixtures/usage-by-table.jsonl shows the result shape if the query is slow.

**Speaker explanation:** Volume by table is where cost decisions start, because DCRs and table plans are set per stream and per table.

**Attendee takeaway:** Start cost work from billable volume by table, not from a guess.

## 4. Weigh the stage records per order

Mode: read-only

Show what the order evidence costs per order: rows and billed bytes per order from the stage table. This is the evidence that answers 'which stage failed for this customer'.

```powershell
$q = Get-Content "$S/src/queries/stage-record-volume.kql" -Raw
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** About seven rows per completed order and a small number of bytes per order, split by Environment and DemoTag.

**If this fails:** Division errors or zero orders: no rows with CorrelationId in the last day; check the time range.

**Speaker explanation:** The most valuable evidence in this session is also among the cheapest. Cost reduction should start where volume is high and diagnostic value is low.

**Attendee takeaway:** Weigh each table's cost against the question it answers.

## 5. Name one reduction and the question it would lose

Mode: read-only

Record one decision using the structure from the previous slides: what to reduce, how (DCR filter, sample rate, table plan or retention), the expected saving, and the diagnostic question that would no longer be answerable. Do not apply it on stage.

```powershell
@"
# M05 decision record ($((Get-Date).ToUniversalTime().ToString('u')))
Reduce: <table / stream>
How: <DCR transformation | sample rate | table plan | retention>
Expected saving: <GB per day from the volume query>
Question we would lose: <for example: per-minute CPU during an order failure>
Owner and review date: <name, date>
"@ | Tee-Object -FilePath $S/evidence/local/m05-decision.md
```

**Expected evidence:** A written record naming one reduction, for example Perf sample interval from 60 to 300 seconds, with the question it loses (minute-level CPU correlation during an order failure) and an owner. The stage records are not the reduction.

**If this fails:** If the volume data is too thin to size a saving, record the decision with the reason and a review date.

**Speaker explanation:** Every reduction removes an answer. Naming the lost question is what makes it a decision instead of a cut.

**Attendee takeaway:** Record every telemetry reduction with the diagnostic question it gives up.
