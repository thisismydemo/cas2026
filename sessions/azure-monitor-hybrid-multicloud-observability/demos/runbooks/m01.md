# M01 — Prove each evidence route

Slide 16 · Rehearsal target: 2.5 minutes

Slide 16. Prove, route by route, that evidence from the Arc-connected AWS machines and from the IIC order stages reaches the workspace: which DCR is associated with which machine, how fresh Heartbeat and Perf are, and that order stage records use the direct-ingestion route (dcr-cas26-requests-eus-01, no association). Collection is proven, not assumed from Arc registration.

Any other Arc machine in that RG is outside the service scope.

## 1. Select the machines and the time window

Mode: read-only

Load the demo context and list the Arc-connected EC2 machines in the connector-created AWS resource group with Resource Graph. This fixes the scope: the machines we expect evidence from, their exact resource IDs and their connection state. The time window for every later query is the last 30 minutes.

```powershell
$S = './sessions/azure-monitor-hybrid-multicloud-observability/demos'
. $S/scripts/Enter-DemoContext.ps1 -ConfigPath $S/config/demo.local.json
$arg = "resources | where type =~ 'microsoft.hybridcompute/machines' | where resourceGroup =~ '$($Demo.AwsResourceGroup)' | project name, status=tostring(properties.status), os=tostring(properties.osName), id"
$machines = az graph query --subscriptions $Demo.WorkloadSubscriptionId -q $arg --first 50 -o json | ConvertFrom-Json
$machines.data | Format-Table name, status, os -AutoSize
```

**Expected evidence:** The six IIC EC2 machines with status Connected and their resource IDs. That is the expected source list; Connected proves Arc management, not that any evidence arrives. Any other machine in the RG is outside the service scope: name it and leave it out.

**If this fails:** No rows: wrong subscription or RG name (the connector RG is lower case, aws_<AccountId>). A machine missing from the list: note it and carry on; do not widen the scope to other RGs.

**Speaker explanation:** Start from scope, not from a dashboard. These IDs are the only machines we will accept evidence from in the next steps; Arc Connected is a management fact, not a telemetry fact.

**Attendee takeaway:** List the exact resources you expect evidence from before you query any evidence.

## 2. Confirm each DCR association

Mode: read-only

For every machine, list its data collection rule associations. An association is what binds a machine to a rule; without it AMA collects nothing for that rule, however healthy the agent is.

```powershell
$assoc = foreach ($m in $machines.data) {
    $a = az monitor data-collection rule association list --resource $m.id -o json | ConvertFrom-Json
    [pscustomobject]@{ Machine = $m.name; Rules = (($a | ForEach-Object { ($_.dataCollectionRuleId -split '/')[-1] }) -join ', ') }
}
$assoc | Format-Table -AutoSize
```

**Expected evidence:** Each of the six machines lists dcr-tplabs-cas26-linux-eus-01. A machine with an empty Rules column would have no collection route, and that is the first thing to fix, before any query.

**If this fails:** An authorization error means the identity lacks read on the Arc resource; do not switch identities on stage. An empty list for every machine usually means the wrong subscription context.

**Speaker explanation:** The association is the wiring between machine and rule. We check it per machine, because a single missing association looks exactly like a quiet machine in every chart.

**Attendee takeaway:** Check the DCR association per machine; an installed agent without an association sends nothing for that rule.

## 3. Query Heartbeat and Perf freshness for the Arc-connected AWS machines

Mode: read-only

Run the freshness query scoped to the connector RG. It reports, per machine, the last Heartbeat and the last Perf sample against an expected maximum age. Heartbeat proves the agent can reach the workspace; Perf proves the DCR's counters flow.

```powershell
$q = (Get-Content "$S/src/queries/evidence-freshness.kql" -Raw).Replace('<AWS_RESOURCE_GROUP>', $Demo.AwsResourceGroup)
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** Rows 'Heartbeat / <machine>' and 'Perf / <machine>' with AgeMin inside ExpectedMaxAgeMin (Fresh) for each of the six machines, and 'Stage / <component> / <stage>' rows for the order records. A machine from step 1 that is missing here would be silent: that is a finding, not a healthy machine.

**If this fails:** No rows at all: check the workspace GUID and the RG placeholder. Stale rows: check the machine's AMA extension state and the association from step 2. The stage-record route is examined on its own in step 4.

**Speaker explanation:** Freshness is two numbers: when the last row arrived and how old it may be. A machine that is not in the result is the most important row, because silence is the failure mode dashboards hide.

**Attendee takeaway:** Compare the machines that report with the machines you expect; the missing ones are the finding.

## 4. Check the stage-record route into Cas26Service_CL

Mode: read-only

Order stage records do not come from an agent. The coordinator and workers send them through the Logs Ingestion API to the direct-ingestion DCR dcr-cas26-requests-eus-01, which has a logs-ingestion endpoint of its own and no association. Show the DCR, confirm it has no associations, then read the table schema.

```powershell
az monitor data-collection rule show --ids $Demo.RequestsDcrResourceId --query "{name:name, kind:kind, endpoint:endpoints.logsIngestion, immutableId:immutableId, streams:keys(streamDeclarations), destination:dataFlows[0].outputStream}" -o json
az rest --method get --url "https://management.azure.com$($Demo.RequestsDcrResourceId)/associations?api-version=2022-06-01" --query "length(value)"
$q = 'Cas26Service_CL | getschema | project ColumnName, ColumnType'
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** kind Direct, a logs-ingestion endpoint, one custom stream flowing to Custom-Cas26Service_CL, and 0 associations. The schema lists the contract columns: CorrelationId, OrderNumber, Customer, Environment, Cloud, Origin, Component, Stage, Success, DurationMs, DemoTag, FailureMode and Computer next to TimeGenerated.

**If this fails:** A Direct DCR with an association is a configuration mistake to record, not to fix on stage. A missing contract column is a schema defect: name it, and show src/fixtures/order-baseline.jsonl for the shape the queries expect.

**Speaker explanation:** Two different routes land in one workspace. Agents need an association; the application's stage records use a direct DCR with its own endpoint and no association. The schema shows the contract columns every later query relies on.

**Attendee takeaway:** Application records sent through the Logs Ingestion API use a direct DCR endpoint; they do not need a DCR association.

## 5. Verify freshness and identity

Mode: read-only

Close the loop on identity: which Azure identity ran these queries, and does every Heartbeat row carry the exact Arc resource ID from step 1 rather than just a computer name? Then check the last stage record in Cas26Service_CL.

```powershell
az account show --query "{user:user.name, tenant:tenantId, subscription:id}" -o table
$ids = @($machines.data.id | ForEach-Object { "'$($_.ToLower())'" }) -join ','
if (-not $ids) { throw 'No machines from step 1: fix the scope before checking identity.' }
$q = "Heartbeat | where TimeGenerated > ago(30m) | summarize LastSeen=max(TimeGenerated) by _ResourceId=tolower(_ResourceId) | extend Expected = _ResourceId in ($ids)"
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
$q = 'Cas26Service_CL | summarize LastRow=max(TimeGenerated), Rows=count()'
az monitor log-analytics query --workspace $Demo.LogAnalyticsWorkspaceId --analytics-query $q -o table
```

**Expected evidence:** The presenter identity in the CAS26 tenant; Heartbeat rows whose _ResourceId matches an expected machine (Expected=true), and any row with Expected=false is evidence from outside the intended scope. Cas26Service_CL shows a last row from the latest orders, a few minutes old at most.

**If this fails:** The guard stops the step: step 1 returned no machines, so fix the scope first rather than running an empty in (). Rows with Expected=false: another machine writes to this workspace; name it and exclude it from the service view. An old last row in Cas26Service_CL: no orders have been placed recently; check the order stream before M02.

**Speaker explanation:** Evidence is only useful if we know whose it is. Resource IDs, not names, tie a row to a machine; and the identity running the query decides what we can see.

**Attendee takeaway:** Tie every evidence row to a resource ID and know which identity read it.
